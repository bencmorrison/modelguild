# ModelGuild — agent guide

Lets **Claude Code** collaborate with **other LLMs** (OpenAI, GitHub Copilot, Google Gemini, …) via **[opencode](https://opencode.ai)** as an auth gateway — no API keys stored or managed by this repo. See [README.md](README.md) for the overview and the command surface, [docs/](docs/) for the reader documentation it points at — [setup](docs/setup.md), [configuration](docs/configuration.md), [operations](docs/operations.md) — [CONTRACT.md](CONTRACT.md) for the behavioral spec, The roadmap lives in [GitHub Issues](https://github.com/bencmorrison/modelguild/issues); decision history is in this file, CONTRACT.md, and git history.

> **This file is the shared source of truth for every agent that works here.** Claude Code reads `CLAUDE.md`, whose first instruction is to read and follow this file; opencode reads `AGENTS.md` natively. Keep shared project facts and conventions here so the driver and delegated models work from the same contract.
>
> **`CLAUDE.md` is a pointer, not a second guide: it holds ONLY what this file does not say.** Its first line is `@AGENTS.md`, and Claude Code resolves that import — so **Claude reads this entire file**, and everything in it (PARITY, vendor-not-a-threat-model, provenance, capability cost, untrusted external output) applies to Claude without `CLAUDE.md` restating any of it. `CLAUDE.md` adds only the four things absent here: prefer-evidence, the **Bias Audit** procedure, verify-each-consequential-claim, and preserve-disagreement.
> **Do not "helpfully" copy shared rules into `CLAUDE.md`.** A copy drifts the moment either side is edited, leaving a **delegated model following different instructions than the Claude reviewing its diff**. That is not a hypothesis — an earlier `CLAUDE.md` restated the parity question as *"would I impose the same rule on Claude Code…"* against this file's *"would I impose this on an Anthropic subagent…"*, and the two diverged the day they shipped.
> **This relationship is machine-checked again — structurally.** `CLAUDE.md` was once a *symlink* to this file (divergence impossible by construction); later a regular file guarded by `doctor.sh` (which checked the `@AGENTS.md` import, the four unique guardrails, and a 60-line anti-fork ceiling); then, when the bash `doctor.sh` retired with the bash layer (M12), nothing — `modelguild doctor` does not check this repo-internal invariant, so the thin-pointer shape was hand-held discipline for a while. **`modelguild/tests/check-claude-md.sh` (CI, issue #28) restored the mechanical half:** it asserts the `@AGENTS.md` first line, that `CLAUDE.md` is a regular file (not a symlink), the 60-line ceiling, and that no distinctive literal marker of a shared rule (`default-deny`, `Every script starts with`, the PARITY forcing question, …) has been copied down. What it **cannot** catch is a shared rule *paraphrased in novel words* so no literal marker fires — **that** half is still judgment, held by hand in review. The evidence log and the test suite remain the mechanical controls for everything else.
>
> **Keep it current.** Treat this as living documentation: update it whenever you change a tool, a command, the dev container, or a convention — in the *same* change, not "later". A stale guide misleads the next agent. When you finish a task that changes how the repo works, ask yourself "does AGENTS.md still describe reality?" and edit it if not.

## Architecture

Claude Code cannot run a non-Anthropic model itself, so it calls a **local MCP server** — `modelguild`, a TypeScript stdio server the user registers with Claude Code (per-project or global; `init` no longer writes `.mcp.json` by default) — which fronts `opencode serve` over its HTTP API:

```
Claude Code ──(MCP tool call)──▶ modelguild MCP server ──▶ opencode serve (HTTP) ──▶ GPT / Copilot / Gemini / …
     ▲                                                                                        │
     └──────────────────── reads the other model's answer, then reasons over it ──────────────┘
```

The bash wrapper layer (`ask.sh`/`log.sh`/`panel-models.sh`/`doctor.sh`, and the automated witness) was retired at M12 (2026-07-23); the reference implementation is now the `src/` TypeScript. See [CONTRACT.md](CONTRACT.md) for the behavioral spec.

- **`src/server.ts`** — the MCP stdio server (`name: "modelguild"`; the handshake's `serverInfo.version` is the RUNNING package's real version since issue #151 — `packageVersion(PACKAGE_ROOT)` imported from `src/init.ts` rather than recomputed, so it is right under `npx`, `npm i -g` and a source checkout alike, with the old hardcoded `"0.0.0"` surviving only as the never-throw fallback; contract clause **C76**, asserted in `test/mcp-client.test.ts`, the only test that sees the real handshake — **and that suite is CI-EXCLUDED because it spawns a real `opencode serve`, so this assertion is enforced by a local `npm test` only**). It exposes the production tools — `guild_consult`, `guild_panel`, `guild_research`, `guild_delegate`, `guild_models`, plus the `guild_status` diagnostic — and, on each call, composes the committed layers (`src/config.ts` policy/config/root resolution, `src/policy.ts` model policy, `src/log.ts` evidence layer, `src/client.ts` typed opencode client) against a supervised `opencode serve` child (`src/lifecycle.ts`). **Shutdown is keyed on stdin EOF / MCP transport close, NOT signals** — Claude Code tears the transport down without a signal, and the MCP SDK's `StdioServerTransport` does not watch stdin end on its own, so the lifecycle wires both explicitly or an `opencode serve` orphans (the M1 flagship test proves zero survive). **`@modelcontextprotocol/sdk` 1.30.0 added a third route into that same teardown, and it runs in the benign direction:** `StdioServerTransport`'s constructor now takes a `maxBufferSize` (default 10 MiB) for its **inbound** `ReadBuffer`, and an over-cap `append` throws inside the `data` handler — which the SDK now catches and converts into `close()`, so it reaches the `onclose` the lifecycle already watches instead of being an uncaught listener exception. We pass no options, so the 10 MiB default binds; it caps only what Claude Code sends **in** (tool-call inputs and elicitation replies — nothing near it), and the outbound `send()` path is unchanged, so a large tool result carrying `raw_response`/`activity` is not affected. Capture is **by construction**: the server records the byte-exact prompt/response from the API history envelope as it passes through (`src/log.ts`), not via hooks bolted around a subprocess. **A turn that produces NO answer is a failure, not an empty success (issues #117 and #121, C74):** `guild_consult`/`guild_panel`/`guild_research` refuse it as `empty-answer` — the panel member lands in `error` rather than dropping out as a blank `text` — and `guild_delegate` still does not opt into that check, since an empty report beside a real patch is a successful delegation. **It refuses "nothing was produced on ANY channel" instead (issue #121):** an empty report **and** a turn that made **no tool calls** is `empty-delegation` — #117's failure mode reached the same way (a provider rejecting a listed model id ends the turn with no text and no tool calls). **THE DECIDING COLUMN IS THE TURN'S TOOL-CALL COUNT, NOT THE CAPTURE'S COMPLETENESS, and that correction is the thing to check first if you touch this.** The first cut asked whether the capture had completed and found nothing — and `ignoredFingerprint` marks a capture INCOMPLETE (`ignored-state-incomplete`) for **any repository containing a wholly-ignored directory**, `node_modules/` included, so the refusal was unreachable in most real repos including this one (probed 2026-08-03: `ok:true`, `report:""`, the defect unfixed). A `patchPath === null` column would have blocked it by a second route — the same probe showed `patchPath` is non-null there — and could never have guarded anything, since it holds only where `filesChanged === 0` already does; it is deliberately absent. **A model that reached for no tool cannot have edited a file or run a command**, so capture representability, logging state and crash state are orthogonal; `capture.filesChanged === 0` survives purely as a guard against refusing while a real patch sits on disk, and `turnToolCallCount` is turn-scoped for the BANANA reason (session-wide would fail OPEN on a continuation). **Three shapes stay successes, all live:** empty report + real patch (pinned by PR #120's test), non-empty report + zero edits (probed 2026-08-02 — an approval-bridge rejection), and a **silent tool-using turn** (the model ran commands, changed nothing, said nothing — the gemini review's finding). That last is the stated residual, deliberate: it *did* something, and `structuredContent.activity` and the approval record are where that shows. **Consequences embraced:** the refusal now also fires under `GUILD_LOG=off`, a crashed capture, `ignored-state-incomplete` and outside a git worktree, so "loud on every model-calling tool" is now true without qualification; a scaffolding-only rejected turn is refused with the `scaffoldChanged`/`scaffoldWarning` tamper signal riding out on the failure (**exempting `scaffoldChanged:true` was proposed in review and REJECTED** — scaffolding appears on exactly the turns this catches, so the exemption would disable the refusal in the common case). **Cost stated:** the `completed` entry keeps `exit_code:0`/`capture_state:"complete"` because it records the TURN, which succeeded — the failure is the tool's judgement one layer up and one step later, unlike the read-path row where the throw is the turn's — and the log still separates it from #120's success, which writes a `delegate-diff` entry where this writes none. **The guard is only as good as the extraction's bound, and the first cut had none:** `fetchHistory` returns the WHOLE session and the extractors walked it backwards without stopping, so on a `sessionId` continuation a silent turn inherited the PREVIOUS turn's answer — `ok:true`, a confident answer to a different question, recorded as this call's byte-exact `raw_response` with `exit_code:0` (reproduced live 2026-07-30: turn 1 answered `BANANA`, turn 2 on a quota-exhausted model returned `BANANA`). `finalAssistantText` **and** `servingAgent` now stop at the last `user` message, which keeps the reason the backward walk exists (opencode splits one turn into a tool-only assistant message plus a text-bearing one) while removing its reach into anything the caller did not just ask; a rejected turn's own `info.error` — whitelisted to name/message/statusCode, since `data` also carries the full response headers and body — is quoted in the refusal, because the activity trace it used to point at is empty under `GUILD_ACTIVITY=off`. One behaviour shift, documented not engineered around: a CONTINUED session with `keepSession:false` whose turn answers nothing is now KEPT (the deletion matrix's continued+throw row — the caller owns the id). And `guild_models` was reworded to match what it actually reads, the running serve's **authed provider configuration** (per-provider, not per-model entitlement, so a listed id can still be rejected at call time — which the READ tools refuse as `empty-answer` and `guild_delegate`, since issue #121, refuses as `empty-delegation` when the turn also made no tool calls; loud on every model-calling tool now, with the silent-tool-using residual named above). **No `status`-based filter is offered, and the reason first recorded for that was FALSE:** it said the field read `"active"` for ids that had just failed at call time, which cannot be — those five ids were **absent** from the re-probed payload entirely. What was observed is that `status` carried exactly ONE value across the whole payload (`active`, 25 of 25), so it partitions nothing; that is the better reason. (Provenance: the error was the coordinating Claude's, in the brief the implementation was written against; corrected 2026-07-30 as a correction, not a new finding.)
- **`src/lifecycle.ts`** — supervises the `opencode serve` child: free-port negotiation, readiness, crash-revive, idle timeout (`GUILD_SERVE_IDLE_MS`; `GUILD_SERVE_PER_CALL=1` spawns per call), and the stdin/transport-keyed teardown. The loopback TCP surface it opens is documented in SECURITY.md as an accepted surface. **Free-port negotiation is a TOCTOU the supervisor SURVIVES rather than closes (issue #79):** the probe listener closes before the child binds, so a racer can take the port; a start whose child then dies with a bind-conflict stderr signature retries the whole negotiate→spawn→ready sequence on a **fresh** port, bounded (three attempts) and **narrow in two dimensions**. *Which failures:* a spawn failure (opencode not on PATH), an auth/config error and a readiness *timeout* all fail on the first attempt. *And how fast they failed:* only a child that dies within `PORT_RACE_WINDOW_MS` (5s) counts as having lost the race. **That second gate is a COST bound**: a child dying just short of the readiness deadline was retried at full price, making the worst-case start ~3 × the readiness timeout — **≈90s**, and under `GUILD_SERVE_PER_CALL=1` on *every* call. With the window the worst case is `readyTimeoutMs + 2 × 5s`, **≈40s**. The signature match is `EADDRINUSE` / `already in use` (both the *address* and *port* phrasings) **or `ServeError`** — so another `ServeError`-raising startup failure is retried too, a stated imprecision costing at most ~10s rather than two further readiness timeouts. A `shutdown()` landing while such a failure is being assembled is reported as a shutdown, never as a port conflict. **Letting opencode pick the port was probed and rejected** (issue #79). **The child's stderr is captured, stdout is not (issue #75):** stderr is piped into a **bounded ring** (newest output wins, so memory is bounded and a pipe nobody reads cannot fill and wedge the child), ANSI-stripped and control-sanitized with line breaks kept, fenced as **untrusted child output**, and quoted into all three startup-failure messages: exited-before-ready (now naming the exit code/signal), readiness timeout, and spawn failure — which names the **errno** (`spawn opencode ENOENT`) rather than the old bare "no pid", by waiting a bounded moment for the `error` event Node emits milliseconds after a pidless spawn. That `error` listener is doubly load-bearing: unlistened, a ChildProcess `error` was an uncaught exception that took the whole MCP server down. Failure-proof per C31's posture — every handler is guarded, so a broken capture degrades the message and never the lifecycle — with one counter-intuitive rule the tests pin: **the drain timer is deliberately NOT `unref`'d**, because with it and the stderr stream both unref'd a grandchild holding the pipe open leaves zero refs on the loop, Node exits mid-await, and the rejection is swallowed outright rather than delayed. Covered offline by `test/serve-stderr.test.ts` (a fake `opencode` first on PATH; the swallow case runs in its own process — the only place "the loop had no other work" is true).
- **`src/worktree.ts` + `src/servepool.ts` — the READ ROOT (issue #96, maintainer decision 2026-07-29).** `/guild:review` could not review branch work. `opencode serve` runs with a cwd and opencode's own `external_directory` permission fences its `read`/`grep`/`glob` inside it; the hardened defs are default-deny allowlists, so `external_directory` resolves to **deny** and every read against a sibling git worktree was refused. **PARITY, not security** (see the PARITY entry below). **All three findings are PROBED on opencode 1.18.7 (2026-07-29), not inferred.** (1) The denial is a function of the serve child's **cwd**. (2) opencode resolves agents from the **serve's cwd**, NOT from the git repository: so the def-presence pre-check moves with the child (`resolveAgentDefDir`'s `projectDir` option) or the feature breaks silently. (3) Rooting a serve at a directory that contains `.opencode/` makes opencode scaffold `.opencode/node_modules` (+ `package.json`/`package-lock.json`) **into that worktree**, while a directory with no `.opencode/` at all is left untouched. **The fence is `git worktree list`:** `resolveWorktreeTarget` realpath-resolves the target and requires exact membership in the worktrees of the repository the server already resolved. Not in the list — an arbitrary path, a worktree of a **different** repository, a path that does not exist, a git that will not answer — is a `worktree-invalid` **refusal naming the path**, never a silent fall back to the project root. **A SECOND supervised child, not a restart:** `ServePool` keys an `OpencodeLifecycle` per root, so each inherits port negotiation, readiness, crash-revive, idle timeout and teardown unchanged. The pool registers **one** callback on the primary's new `onShutdown` hook rather than duplicating the stdin-EOF/transport-close wiring the M1 orphan proof rests on. **That hook fires on TEARDOWN ONLY, and the distinction is load-bearing** (issue #96): `shutdown()` is *also* how the idle timer and per-call mode retire a child. Companions therefore run for **every** shutdown reason **except `idle` and `per-call`** — a two-name exemption with a **teardown default**, so a reason added later can only be too eager (a respawn), never too lax (an orphan). Reclamation is not lost, it is per child: every extra is a full lifecycle with its own idle timer and per-call mode. The **process-exit/signal backstop is now installed once per PROCESS over a registry** rather than once per lifecycle. *Cost, stated:* a second root means a second loopback port, a second `/event` subscription, a second idle timer and a second process; nothing caps the count but the repo's own worktrees and the idle timeout that reclaims them. **A CONTINUATION'S ROOT COMES FROM THE SESSION, NOT FROM THE CALL** (issue #96): opencode keys sessions by **project**, and a worktree and its main checkout are the same project. So `GET /session/{id}`'s `directory` is the authority: a continuation is routed to the session's own tree (the caller does not repeat `worktree`), an explicit `worktree` that **disagrees** is an error naming both, and a session whose directory is not a worktree of this repository is a **refusal**, never a guess. **A session that cannot be FETCHED is scoped, not absolute:** it refuses only when the answer could actually differ — when this call named a root, or when some other root has already been routed in this server's life. With neither true, the primary child is the only one that exists, the lookup decides nothing, and the call proceeds exactly as it did before #96. *Stated cost:* every continuation now makes one short control-plane GET **before** the model-policy gate, so a continuation naming a denied model ensures a serve is up on its way to being refused — no model turn, nothing logged, and a fresh call is unchanged. **The read root is recorded in the RECEIPTS** (issue #96): the `started` entry carries `read_root` when a non-default root was used. Written only when supplied, so an untargeted call's entry is byte-identical to one written before the field existed. **Scope at #96: the READ tools only** — `guild_consult`, `guild_panel` (panel-WIDE: members reading different trees would be incomparable while looking as if they disagreed), `guild_research`. **`guild_delegate` was excluded, and issue #107 included it — see the WRITE ROOT entry below**. Covered offline by `test/worktree.test.ts`.
- **THE WRITE ROOT — `guild_delegate` into a sibling worktree (issue #107, maintainer decision 2026-07-29).** Same input, same fence, same refusal: a `worktree` on `guild_delegate`, validated by the SAME `resolveWorktreeTarget` choke point, refused by name as `worktree-invalid` (exit-analogue null) before any log write **and before any snapshot**, routed through the SAME `ServePool`. **PARITY, and the maintainer's own argument (see the PARITY entry below).** **THE WHOLE POINT IS THE COUPLING, and it is the thing to check first if you touch this file.** #96 moved the serve child's cwd; it did NOT move the capture layer's root. Doing only that here would let the model edit one tree while the snapshot, the baseline/after trees, the ignored fingerprint, `scaffoldDigest`, the recovery hint and the recorded patch all described another — **and the result would still say `captureComplete:true`**. So the root is resolved ONCE (`resolveReadRoot`, now returning an always-present `root` beside #96's optional `worktree`) and the single value is threaded to the serve child *and* every capture consumer. **That is a discipline, not a proof — do not restate it as "by construction"** (issue #107): `cwd` stays in scope because the evidence log legitimately takes it (the log root is deliberately NOT re-rooted at the target). **The behavioural fixtures are the net** — they mutate one tree while targeting the other and fail loudly the moment the roots diverge. **The recovery hint names the tree** (`git -C <worktree> checkout …`) — a worktree shares its main checkout's object database, so the bare form pasted in the wrong tree restores *successfully* into the wrong tree; an untargeted call's hint is unchanged. **The receipts get `write_root` on `started`, NOT a reuse of `read_root`:** "this tree was mutated" is a different claim from "the answer describes this tree", and folding them would make *which trees did a model change?* return every read-only consult that named a worktree. C29's optional-field rule, so an untargeted delegation is byte-identical to pre-#107. **The approval bridge parses the def in force in the TARGET tree** (`approvalFor` gets the re-rooted `agentDefDirs`), so the never-widen invariant (issue #20) holds on this axis instead of silently reading the project's copy. **#96'S KNOWN UNKNOWN IS CLOSED:** opencode materializes `.opencode/node_modules` + manifests into a serve's cwd **iff that cwd already contains an `.opencode/` directory**, and it happens on the **first request that loads the plugin runtime** (`GET /agent` and `POST /session` both do), **not** at serve start. **THE PRECONDITION IS RECORDED AT BASELINE, NOT INFERRED** (issue #107): `WorktreeSnapshot.opencodeDir` captures whether `.opencode/` existed *before* the turn, because afterwards it exists either way. **The `scaffoldChanged` flag never varies; only the warning text does, on that checked precondition**, across three cases: an existing plugin dir *modified*; scaffolding *appearing* where `.opencode/` was already present; and scaffolding *created* where `.opencode/` was **absent**, which opencode does not do, so it is reported as an **unexplained** write with no benign reading offered. **Pre-warming the child before the baseline snapshot was considered and REJECTED** — it would pin the write path's evidence baseline to an undocumented lazy-load ordering in a dependency this repo tracks unpinned, to buy one suppressed warning per tree. *Cost, stated:* a delegated model can now edit and `bash` in a worktree the caller named, so SECURITY.md's accepted trusted-repo exposure for `guild-build` (any repo file including credentials — #29 residual 1 — and `bash` reaching the network) extends to that tree. The human diff review remains the boundary — **of a diff that must be of the tree actually edited.** *Two named residuals:* `GUILD_AGENT_DIR` returns before `projectDir` is consulted (`resolveAgentDefDir`), so with it set the def pre-check **and** the approval bridge's allow-set read that dir while opencode still resolves from the serve cwd + global — the never-widen invariant then holds against a def that is not in force. And `write_root` rides on `started` only, so the `delegate-diff` entry does not itself name the tree, and the patch lives under the **project's** logs whichever tree was edited; the pairing is by `call_id`. Covered by `test/delegate.test.ts` section H.
- **THE SCAFFOLD LEAVES THE STAGING TOO — `src/snapshot.ts` (issue #108, maintainer decision 2026-07-29).** `snapshotTree` stages the throwaway index with `git add -A`, which honours `.gitignore` — so the serve-scaffolding exclusion the ignored-file fingerprint has applied since 2026-07-22 was reaching the recorded PATCH only by luck. opencode writes an `.opencode/.gitignore` covering everything it materializes but **does not overwrite an existing one** (probed, C70), so a repo that **commits its own** never receives opencode's: the scaffolding is untracked-but-not-ignored, `git add -A` stages every path of it, and thousands of paths land in `modelguild/logs/<run_id>/diff-<call_id>.patch` — the artifact the human diff review reads, which SECURITY.md names as the write path's only trust boundary. **The fix is `unstageUntrackedScaffold`, and it reuses the exclusion the project already ratified rather than inventing one:** after `git add -A`, every `isServeScaffold` path in the index that the repository does not **track** is dropped with `git update-index --force-remove` (NUL on stdin — a materialized `node_modules` would blow ARG_MAX on argv). **Scoped to untracked** because pollution is by definition newly created files — a repo that commits `.opencode/package.json` owns it, and the model's edit to that file stays in the diff like any other tracked file. **ONE CODE PATH IS NOT ONE RESULT** (review, 2026-07-29): both snapshots do go through `snapshotTree`, but the predicate's second input — *is this path tracked?* — was read from HEAD **separately in each call**, and `guild-build` allows `bash`, so a delegated model running `git add -A && git commit` moves HEAD mid-turn. The property is held by one code path **plus** a tracked set resolved ONCE at the baseline (`WorktreeSnapshot.trackedScaffold`) and threaded to the after-snapshot through `CaptureInput`. **THREE THINGS DELIBERATELY UNTOUCHED.** `scaffoldChanged` is unchanged and still fires — it is the ratified condition the whole exclusion rides on, and suppressing a tamper signal because a benign explanation exists is that signal's one unforgivable failure. `.opencode/agent/**` is not in `isServeScaffold` and stays fully in the fingerprint and the patch: a bash-capable model tampering with a hardened def is precisely what capture must never drop. And nothing about `captureComplete`, the recovery hint or `write_root` moves. *Capability cost, stated, and it is sharper than "a write is now absent from the patch":* the write this hides is a write into a directory `opencode serve` **loads and executes**, and in the COMMON shape — a model writing a plugin on the first delegation into a tree that already had `.opencode/` — `scaffoldChanged`'s three-case wording (#107) correctly selects the **benign** branch. So the patch shows nothing and the surviving signal reads as housekeeping. What still catches it: that warning (read as a prompt to look at the directory, not as an all-clear), the activity trace's file-edit lines, and `git status` in the tree. **Two known limits, named not engineered around:** `update-index`'s exit status is unchecked (a failure leaves the paths staged — the pre-#108 noisy patch, the safe direction — but silently), and a regular file or symlink at `.opencode/node_modules` is dropped by the predicate while `scaffoldDigest` records only an error marker for it, so a change to such a path is invisible in both surfaces. Contract **C37/C38/C40**; covered by `test/delegate.test.ts` section I. **INTERACTION WITH #111's RESOLVED-AGENT GATE.** `node_modules` lands hundreds of ms to seconds AFTER `GET /agent` returns (measured; see the #111 bullet below), so it is *not* on disk at baseline time; with `unstageUntrackedScaffold` in force the untracked scaffolding is stripped from the index of **both** snapshots, so it sits in **neither** tree rather than cancelling in both. **That is the point, and it is why the exclusion and not the ordering is the guarantee:** `unstageUntrackedScaffold` is timing-independent, so it holds no matter when opencode writes. The two baselines are still taken at deliberately different moments and neither may be moved to match the other — the scaffold DIGEST above the gate (or the severe MODIFIED wording fires on every first delegation, review A1), the git tree below it (or a refusal snapshots a tree it was never going to touch).
- **`src/init.ts` (`modelguild init`)** — the installer. It supports a **per-project install (default)** and a **`--global` install**; the payload SOURCE files are identical, only the destinations differ.
  - **Per-project (default):** the 8 command docs → `.claude/commands/guild/`, the 3 hardened agent defs → `.opencode/agent/`, the policy/config templates → `modelguild/`, a fenced git-ignore block, and the ownership record at `modelguild/.modelguild-install.json`.
  - **`--global`**: the same payload lands in the user's global config so `/guild:*` + the agents work in **every** project with one install — commands → `<homeDir>/.claude/commands/guild/`, agent defs → `<xdgConfigHome else ~/.config>/opencode/agent/` (SINGULAR `agent`, the dir opencode resolves `--agent` from in any project), policy/config → `<homeDir>/.claude/modelguild/` (the server's existing `~/.claude/modelguild/` root fallback), and a **separate** ownership record at `<homeDir>/.claude/modelguild/.modelguild-install.json`. Global mode takes no `--dir` and writes no `.gitignore` block (there is no project); `--write-mcp` is rejected. Plain `doctor` (no `--global`) detects a global install too — it counts each payload piece present if found in **either** the project OR the global location (mirroring runtime resolution), so a global-only install does not falsely fail; `doctor --global` is the explicit "check ONLY the global locations". `install.sh --global` now means both a global CLI and a global payload.
  - **MCP registration is user-driven by default: `init` does NOT write `.mcp.json`** in either mode (maintainer decision, `feat/user-installs-mcp`). The user registers the server themselves with `claude mcp add modelguild -s <scope> -- <launch>` and chooses the scope — `user` (global, all projects, in `~/.claude.json`), `project` (committed `.mcp.json`), or `local` (private). On a default install the CLI prints both the `claude mcp add` line and a hand-placeable `.mcp.json` snippet; `mcpAction` is `"skipped"`. The opt-in **`--write-mcp`** flag (per-project only) restores the old auto-write — merging a project-scoped `.mcp.json` entry under the key `modelguild` (the exact key the command grants `mcp__modelguild__<tool>` require). Either way the key must be exactly `modelguild`.
  - Ownership is SHA-256-based in both modes: a re-install upgrades a file only while its bytes still match what init wrote; a user-edited file is skipped (never clobbered) with a warning; `--uninstall` (add `--global` for the global payload) removes only hash-verified files. **The `.mcp.json` `modelguild` key follows the SAME ownership rule (issue #32):** a `--write-mcp` install records `{ mcp: { key, entryHash } }` (sha256 of the entry it wrote) in `modelguild/.modelguild-install.json`, and uninstall deletes the key ONLY when that proof is present AND the current entry still hashes to it — a `mcpAction` of `"removed"`. A user-created key (default install never touches `.mcp.json`), a user-**edited** entry (hash mismatch), or a **legacy** record with no `mcp` field are all `"kept"` with a warning, never deleted (fail-safe: never remove what init cannot prove it wrote). Covered by `test/init.test.ts`.
  - **SYMLINKS AT A DESTINATION DIFFER BY MODE (issue #156, maintainer decision 2026-08-05).** Project mode is unchanged: `safeJoin` refuses a symlink at any existing component. **`--global` follows DIRECTORY-component symlinks** (`globalJoin` — same `..`/absolute guard, no per-component refusal), because a dotfiles manager (GNU stow, chezmoi, a hand-rolled `ln -s`) makes `~/.claude` and `<xdg>/opencode` symlinks, and the old rule made `--global` throw `refusing destination symlink: …` at the first linked destination. **What that cost depends on WHICH link:** with `~/.claude` linked, `planFor` resolves the ownership record's path (under `~/.claude`) **eagerly**, so the throw lands before the install loop starts and **zero** files are written; with only `<xdg>/opencode` linked that resolution succeeds, the 8 command docs land, and the first agent def throws — a **partial** install with no ownership record (both probed on `origin/main`, 2026-08-05). **In GLOBAL mode a leaf payload-file symlink is neither followed nor refused:** it takes the existing never-clobber branch — skipped with a warning, the rest of the payload installs, the ownership record is still written. (**Project mode keeps refusing a LIVE leaf link** by name; the leaf rule is global-only.) The install loop's existence test is now `lstat`-based so a **dangling** leaf link reaches that branch in both modes, and that is **two** behaviour changes in project mode from one root cause: a dangling leaf was written *through* (payload bytes outside the target), and where the link's target directory did not exist that write was a mid-loop `ENOENT` crash. Both are now a clean skip. **The ownership record's own path is the exception, and it WARNS:** `writeRecords` sits outside that branch, so a symlink there is written through, live or dangling — deliberately (only init writes the record, so there is no user content to preserve) but no longer silently: the warning names the link and the file the bytes actually landed in. **TWO enumerated shapes are REFUSED instead, at plan time with nothing written:** a `--global` **dangling** record link whose *target's* directory does not exist, or is not a directory. `writeRecords` creates the LINK's directory, not the target's, so those writes were a raw `ENOENT`/`ENOTDIR` **after the whole payload was already on disk** — no ownership record, a re-run crashing identically, and an `--uninstall` that can prove nothing is ours. `assertRecordLinkWritable` refuses both inside `planFor`'s eager record-path resolution, naming the record, the target and that directory, with distinct wording per condition; **creating or replacing that directory was rejected** as a bigger step than declining, and this is **two named conditions, not a general can-this-write predicate** — any other cause still fails from the write. Install-only (`--uninstall` writes no record, so it must not be blocked) and global-only — project mode still throws from that write, as it did on `origin/main`. *Capability cost, stated:* `--global` now writes wherever those directory links point, including outside `$HOME`, and uninstall's `pruneEmptyDirs` may `rmdir` now-empty directories inside the backing store; nothing bounds where a wrong or hostile `~/.claude` link redirects the whole payload. *Provenance:* the ask and the global-only scope are the maintainer's (issue #156); the shape is Claude's. Contract clause **C77**; covered by `test/init.test.ts`.
  - **UPGRADE DRIFT is the never-clobber rule's cost, and it is now REPORTED (issue #22).** A file is **drifted** when three hashes are all distinct: the **recorded** hash (proof init wrote it, and which version the edit was based on), the **current** bytes (≠ recorded ⇒ the user edited it), and the **shipped** bytes (≠ recorded ⇒ the release moved on since that edit). `isDrifted` in `src/init.ts` is the single predicate; `init` reports it from the run it just did (`InitResult.drifted`, per file `{ dest, installedPath, shippedPath, installedHash, shippedHash }`) and `doctor`/`guild_status` from the standalone `scanPayload`/`scanInstalledPayload`. Two neighbouring states are deliberately **not** drift: an edit against the version the release still ships (recorded === shipped — nothing to catch up to), and a file with **no** record (never ours — the `shadowed` case; calling it stale would be a guess). **Report only: the file is still never touched, and no `--force`-style flag is offered**. The hint is a paste-able `diff "<shipped>" "<yours>"` plus delete-and-re-run-`init` to re-adopt the release. **Drift is a WARNING, never a failure** — `doctor`'s exit code is unchanged by it. Mode-correct in both directions: the record consulted is the one for the mode/location the file was found in (`recordPathFor`, routed through `payloadDest` so the project/global mapping cannot drift from the payload's), so a `--global` install is judged against the global record. **What `doctor` honestly cannot do:** with no ownership record, an intentional edit and a stale leftover are byte-identical evidence — those are reported as *unjudgeable*, naming the missing record path, rather than guessed as "stale". Covered by `test/init.test.ts` and `test/doctor.test.ts`.
  - **PAYLOAD SKEW: the server updates itself, the payload does not — and now it says so (issue #94, 2026-07-29).** `.mcp.json` runs `npx -y modelguild serve`, which resolves the current release **on every launch**; the command docs, agent defs and templates `init` wrote live in the *user's* repo and stay put. So a user upgrades the server and keeps running last release's `/guild:*` commands and hardened defs, silently and indefinitely. Three states, one comparison, and the distinction is the whole change: **drift** (`recorded ≠ current`, `recorded ≠ shipped` — edited *and* the release moved on; report, never overwrite), **skew** (`recorded === current ≠ shipped` — untouched, simply behind; `npx modelguild init` fixes it *in place*, precisely because it still passes the ownership check), **unjudgeable** (no record — an intentional edit and a stale leftover are byte-identical evidence, so it is **not** reclassified as skew). Edited-against-what-the-release-still-ships stays deliberately *nothing*. **"Shipped" is the payload of the package the RUNNING code was loaded from** — `PACKAGE_ROOT`, derived from `import.meta.url`, correct under `npx` and `npm i -g` alike, and not redirectable by a cwd or an env var; `cli.ts` imports it rather than recomputing it. **`scanInstalledPayload` is the ONE detection, surfaced three times** — `doctor`, `guild_status` (`structuredContent.payload`, carrying the deciding installed-vs-shipped hashes), and the server's start-up notice — with the project-then-global location (`locatePayload`) and the record-for-that-location both routed through `payloadDest`/`recordPathFor`. **Skew never changes `doctor`'s exit code**, same as drift: behind a release is not broken. **`init` reports drift but never skew** — an untouched file passes the ownership check, so the only run that could observe it has just fixed it. **Direction is NOT claimed:** two hashes cannot carry it and the record holds no version, so "yours is older" is an *inference* from how the pieces update — right normally, wrong for someone who pinned an older server deliberately. Every surface says the files are **out of sync with what this server ships**. Contract clause **C72**; covered by `test/init.test.ts` and `test/doctor.test.ts`.

So the `latest` refresh is **atomic** (temp symlink + `rename`) and skipped when the link already names the run — `ln -sfn`'s unlink-then-symlink hole was being entered on every append, and `modelguild watch` re-resolves `latest` on every poll — and **`latest()` answers only when the run dir still exists**, so a pointer a concurrent prune has outlived reads as *no latest run* instead of sending the watcher at a deleted run — that check, not the dangling-link unlink, is where the guarantee lives (the unlink is hygiene, and its residual race can leave `latest` absent until the next run starts; C34 states it, and there is no backstop). Racing prunes stay data (`skipped`), never an exception, with the accounting limits C34 names. Proven with real racing PROCESSES in `test/log.test.ts` (synchronous fs calls in one process cannot interleave, so a same-process test would prove nothing), with a reader hammering `latest` throughout — it caught both defects on the pre-fix code. Knobs resolve **env override > `modelguild/modelguild.conf.local` > default**. Hashes catch accidental corruption, not adversarial rewriting. **The `run_id` is a DIRECTORY NAME, so it is validated at one choke point (`#resolveRun`, issue #73, CONTRACT.md C33a) on both supplied paths — a tool's `runId` input and `$GUILD_RUN_ID`:** a single conservative path segment (no `/`, `\`, `..`, leading `.`, NUL; length-capped; and not `latest`/`watchers` in any case, which name other things in the same root), or an **error** — a tool input error at the MCP boundary, `ok:false` + a stderr warning naming the source inside the layer, never a silent fall back to a fresh run, and never a write outside the logs root. Two consequences worth knowing before you touch either: a run id the tools did not mint is **never pruned** (C32's fence is the narrower minted shape, and it stays that way — it exists to spare the user's own directories), and any caller that resolves a run dir must guard `log.enabled() && runId.length > 0` first, because with logging off the id is `""` and resolution would fall through to `$GUILD_RUN_ID` — that missing guard on the delegate path is what let a hostile env var throw out past the capture (C31), fixed with the grammar. Covered by `test/log.test.ts`. **These are receipts you read yourself** — when Claude says "GPT-5 agreed", the log holds the model's actual words for you to check.
- **`src/activity.ts` — the live-activity layer (issue #20).** The evidence log is a *post-hoc* record; this is the **liveness**. One `GET /event` SSE subscription per `opencode serve` child (`ServeEventBus`, refcounted, routed to concurrent calls by `sessionID` so a 3-model panel costs one stream), normalized and written line-by-line to a git-ignored `modelguild/logs/<run_id>/activity.jsonl` **while the turn is still running** — which files the external model read, what it grepped, fetched, edited, and which shell commands it ran. Three surfaces: `npx modelguild watch` tails it live (the primary channel — a file and a terminal, depending on nothing else), every tool result carries a bounded `structuredContent.activity` (counts by tool, files edited, errors, the first N action lines, `degraded`), and **`src/progress.ts`** relays each event as an MCP `notifications/progress` when the client sent a `progressToken` (throttled to one per second — the LATEST event in a window is flushed, intermediate ones live only in `activity.jsonl` — plus a heartbeat through a quiet stretch, which is what stops a legitimately slow turn tripping Claude Code's MCP idle watchdog). It is a **separate module from `src/server.ts` on purpose**: importing `server.ts` constructs the MCP server and connects the stdio transport at module top level, so the emitter could not otherwise be unit-tested. Nothing in it may throw into a tool call — `sendNotification` can reject *and* throw synchronously, and it is called both before the tool's own `try` and from a `setInterval`, where an escape would take the process down. **The normalizer is built on PROBED events, not the API's documented union:** the source is `message.part.updated` with `part.type === "tool"` (whose `state.status` walks pending → running → completed|error and carries `tool`/`callID`/`input`/`output`/`metadata.exit`), plus `file.edited`, `permission.*`, `session.idle`, `session.error`; the `session.next.tool.*` names exist in opencode 1.18.5's union but **never fired** across the ~6 turns probed on 2026-07-27, so they are understood but not relied on. **Two payload facts cost real behaviour and are pinned by tests** (found by review on 1.18.7, after the fixtures had been written from the design's table rather than from a capture): a `pending` tool part carries `input: {}` — only `running` has the command — so `pending` is dropped and `tool-called` is emitted on `running`; and `file.edited` carries `{file}` with **no `sessionID`**, so session-less events are broadcast to every subscriber of that serve child and flagged `unattributed` rather than dropped (dropping them left `filesEdited` permanently empty in production while the fixture, which had invented a `sessionID`, stayed green). The panel cost is stated rather than hidden: with two write-capable calls on one serve child an edited path is attributable to the child, not the member. Unknown event types are **dropped silently** (an opencode bump must never break a call), and **a stream failure is never a call failure** — the bus reconnects with backoff and, failing that, the result reports `activity.degraded` with a reason, so a quiet activity list is never mistaken for a quiet model. **The bus also signals a RE-attach** (`BusHandlers.onReattached`, issue #91) — never on the first connect, since a subscriber that attached there missed nothing. The bus replays nothing and knows nothing about what was lost; it is a bare "you were blind, and now you are not" edge, and the approval bridge is the only subscriber that acts on it (`activity.degraded` still latches for the call, because a hole in a trace does not heal). **It is NOT the evidence log and does not touch it:** `activity.jsonl` is a separate file, no `calls.jsonl` entry shape changed, no entry references it, and `verify()` never reads it. **It is not containment either** — watching a `bash` call scroll past does not gate it; the human diff review is still the review point. `GUILD_LOG=off` mints no run dir, so nothing is written (turning the record off must not leave a different record on disk). Covered by `test/activity.test.ts` (offline, scripted SSE fake).
- **`src/approve.ts` — the OPT-IN approval bridge (issue #20 slice 4, shipped 2026-07-28).** Watching is not gating; this makes the model ask **before** it acts. When `GUILD_APPROVE` (write path) or `GUILD_APPROVE_EGRESS` (read paths' web egress) is set, the tool creates its session with a per-session `ask` ruleset via `POST /session`'s `permission` field and answers each resulting `permission.asked` off the SAME `ServeEventBus` the activity layer uses. **The bridge changed no hardened agent def** — it injects its `ask` rules per SESSION, never into `.opencode/agent/`, so `check-agent-permissions.sh` and `verify-guild-*.sh` still assert exactly what they assert today.
  - **THE HONEST BOUND, stated wherever this feature is described (maintainer Q3, 2026-07-28): an approved `bash` is an approved SHELL.** The prompt shows a command string; that command can read credentials, reach the network, and spawn processes that raise no further requests. The bridge buys **attention and an interrupt**, not containment — the human **diff review** remains the write path's review point. Do not let a later doc quietly upgrade this into a guarantee.
  - **Two mechanical invariants, both load-bearing because the session ruleset MERGES (probe P2) and can override in both directions.** (1) **Never emit `allow`** — the one-line ruleset that proved the merge (`[{bash,*,allow}]`) handed a working shell to `guild-read`; asserted in `buildApprovalRuleset` **and again** at the wire boundary in `createSession` (`assertAskOnlyRuleset`), so no future caller can route around the module. (2) **Never gate a tool the agent does not already allow** — `ask` on a DENIED tool converts it into an approvable one, so gated tools are the INTERSECTION of the tier's tools with that agent's own allow-set — **parsed from the agent def in force** (`resolveAgentAllowSet`), never from a hard-coded mirror of the shipped defs. A def that cannot be found or parsed **refuses to arm**, naming the file — fail-safe by construction. Consequence: `GUILD_APPROVE` alone gates **nothing** on the read paths.
  - **Arming with no answering channel is REFUSED up front**, before `log.expect()` and before the delegate worktree snapshot (same gap-parity discipline as `agent-def-missing`). This is not tidiness: probe P3 showed an unanswered `ask` under `opencode serve` **hangs** the turn until `GUILD_MESSAGE_TIMEOUT_MS` — it does *not* fail closed — so arming blind would deadlock. Channels are (1) **MCP elicitation**, issued as a RAW `server.request({method:"elicitation/create"})` with an **EMPTY-field `requestedSchema`** so the client's own **Accept/Decline** buttons are the decision in one keypress. All context moves into the message, since no field remains to carry it, and **only the literal action `accept` approves**; and (2) the **`modelguild watch --approve` terminal**, which announces itself with a heartbeat presence file under `<logDir>/watchers/` (fresh mtime **and** a live recorded pid — corpses are reaped, and SIGINT/SIGTERM retract the file rather than leaving one) and **replies to the loopback serve port itself**, so the server never proxies its decision. Both may answer: **first reply wins, opencode arbitrates** (a second reply to a settled id is a 404, verified on 1.18.7). **But elicitation must not PRE-EMPT the terminal** (issue #20). So a **cancel ABSTAINS** while another live channel could still answer, and **rejects** only when elicitation is the sole channel; an explicit **decline** always settles.
  - **Fail-closed timeout, and no self-approval.** An unanswered request is rejected after `GUILD_APPROVE_TIMEOUT_MS` (default 120000) via the message-carrying `POST /permission/{id}/reply`, and the reject message reaches the model **verbatim** (probe P3) — a denied tool call it reasons around, not an aborted turn. Approvals go to the session-scoped `POST /session/{id}/permissions/{permId}` (it cannot answer another session's request by mistake). There is **no tool input** by which the driver can pre-approve anything, and `test/approve.test.ts` asserts no tool's input schema grows one.
    - **A REFUSED reply is CHECKED, not assumed (issue #97; CONTRACT C68).** "First reply wins" produces a 404 — and so would the removal of `permission.respond`, the **approve** endpoint and the only operation opencode 1.18.7 marks `deprecated`, which would fail every approval while rejections kept landing. Booking both as `contested` let a quiet counter absorb an approval-only outage, so **any non-2xx opencode actually answers** is now followed by one bounded `GET /permission` (the same v1 snapshot the #91 re-list reads, own-session filter and all). **The whole non-2xx range, not the 404 alone.** **Still open ⇒ `unsettled`** — a counter distinct from `contested` *and* from `undelivered`, because the reply reached opencode and was refused, which is neither a race nor a transport failure — carrying an `unsettledReason`. **Not open ⇒ the cause is claimed only where the status supports it:** a **404** is `contested` (the documented race, now one the bridge went and looked for); **any other status is `refused`** — observed, undiagnosed, because stretching `contested` over a 410 would re-create the overload this change removed from it. **The check unable to answer, or the list carrying an entry it could not attribute ⇒ neither CLAIM** — the request is still counted in whichever of those two the status selects, but recorded `still_open: null`. **`undelivered` is now the transport arm alone** (nothing came back, no status to reason from), and the check is deliberately not run there — it would be asking a serve just proven unreachable. Every record carries the real `http_status` and the bucket it was counted in, so a 404 and a 410 are told apart without diffing counters. It **does not feed `degraded`** (which since #91 means "blind NOW" and clears on evidence — a bridge that can see and cannot deliver is a different failure, and a clean re-list would erase it), it may never throw into a call, and it decides nothing.
    - **Three counter properties (issue #97).** (1) **`unsettled` is not refusal-only, and excludes a reply IN FLIGHT.** The re-list's "we answered it and opencode still lists it open" case feeds it too — including after a **2xx** that did not take effect — but `#claimed` means *started answering*, not *the answer landed*, so a re-list arriving mid-reply must read the request as in flight and count nothing. `#replied` — set when the POST returns or throws — is the gate; an in-flight request is recorded (`relist-inflight`), counted nowhere, and does not keep the bridge degraded. (2) **The four buckets are disjoint and never sum past `requests`**: one classification per request id, a later observation superseding an earlier weaker one (`unsettled` is the only positively-confirmed bucket, so it wins and is terminal). (3) **`unsettledReason` keeps the most informative reason, not the first**: an approve-path refusal (deprecation + status + re-probe command) outranks any other refusal (status, plus an explicit note that the reject endpoint is *not* the known expiry condition), which outranks the re-list arm (neither).
    - **The BLIND WINDOW is the stated exception to that clock (issue #77, NARROWED by the re-list in issue #91; CONTRACT.md C68).** The approval timeout only ever starts on a request the bridge **saw**. Lose the SSE stream while armed and open requests are rejected fail-closed with `approval.degraded` set. **On re-attach the bridge now asks opencode what is still open** (`GET /permission`, probed live on 1.18.7 — global to the serve child, so the **own-session filter is load-bearing**: on a panel it is what stops one member's bridge answering another's) and routes what it finds as if the event had arrived, **skipping ids it has already settled or replied to** so a request rejected on the degraded path is never re-prompted. The unseen window becomes the reconnect backoff instead of the turn's backstop. **The guarantee is "recovered on re-attach", never "never missed"** — the endpoint lists what is still OPEN, so a request raised *and* settled by somebody else while blind leaves nothing to find; a failed `GET /permission` degrades and never throws into the call. Nothing runs ungated in any case (opencode holds the call at its `ask`); the residual cost is a **stall**, accepted deliberately over aborting a turn on a transport blip. **`degraded` now means "blind NOW" and can CLEAR** — only on evidence (re-attached, list answered, everything routed, nothing we already decided still open); `blindWindows` is latched in its place and is the caveat on every other counter: recovered is not the same as nothing was missed.
  - **A ruleset is fixed at session creation.** The bridge verifies it actually took — opencode echoes the stored ruleset on create and on `GET /session/{id}` (verified 1.18.7) — so an opencode build that ignored the field, or a **continued** session created before the knob was armed, is an `approval-not-applied` refusal rather than a turn that runs ungated while the caller believes it is gated. A session created *with* the rules continues fine (the workshop round-1→round-2 flow still works under the egress knob).
  - **The whole bridge is pinned to opencode's v1 permission surface BY DECISION (maintainer, 2026-07-29; issue #93) — do NOT "modernize" it onto the v2 endpoints.** **The approve endpoint is also the ONLY operation opencode marks `deprecated` on 1.18.7 — a real expiry condition on this pin**, whose handling is in C69a and the in-code record. Revisiting takes a **fresh probe on a later opencode** *and* the live `verify-guild-*.sh`-style proof extended to cover it — the offline suite drives a v1-behaving fake and would go green on a v2 bridge that gates nothing. **The evidence lives in ONE place — the `V1 PIN` block in `src/client.ts`** (everything else, here included, is a pointer; a wrong claim in this record reached five files at once on the day it was written, which is exactly the drift shape this repo warns about). The rule is CONTRACT **C69a**, and `modelguild/tests/check-v1-permission-pin.sh` (CI) fails a **literal** v2 *permission* path in a non-comment line of `src/` — permission surface only, not the rest of opencode's `/api/` tree, and a split or computed literal evades it by construction.
  - Covered by `test/approve.test.ts` (offline; the fake `POST /session` stores and echoes the ruleset, and a gated turn **blocks** on the reply exactly as `opencode serve` does, so "the tool really waited" is asserted rather than assumed).
  - **Retention is now enforced at three points, not one (issue #23, 2026-07-25).** `GUILD_LOG_RETENTION_DAYS` (default 14; 0 disables) is applied at **server start** (`enforceRetentionOnStart`, called from `src/server.ts` before `connect`), at **`new-run`** as before, and on demand via **`npx modelguild logs clean [--days N] [--dry-run]`**. One resolver (`EvidenceLog.retention()`) feeds all three, so they cannot drift apart. Details in CONTRACT.md C32/C32a; the choices worth knowing here: a run's **age is its newest content**, not the run dir's mtime (a run still being appended to is never pruned mid-flight — the dir mtime only tracks it incidentally, via the `.lock` mkdir); **server start is skipped when `GUILD_LOG=off`** (logging off is a plausible way to say "freeze this"), while `logs clean` still runs because it was asked for in so many words; an **unparseable** window disables pruning rather than falling back to 14; and `logs clean` **refuses** rather than treating an absent/zero window as zero days. Scope: the one resolved logs root, direct children only, run-id-shaped real directories only (never a symlink); under `GUILD_LOG_PARTITION=1` that is the current project's partition, so a sibling project's runs are out of scope and stay put. **With #19's layering, read and write split the way they do everywhere else:** the window is read across all root layers (`guildDirs`), so a global setting binds in a project that never restates it, while only the **primary** root's `logs/` is pruned (`guildDir` = `layeredRoots()[0]`) — the only root runs are ever written to.

## Dev container & auth

- `.devcontainer/` runs Claude Code **and** opencode in-container, both on PATH for the `node` user. **Both are installed by `postCreate.sh`, not the `Dockerfile`, and both track `@latest`** — a Dockerfile `RUN` layer is cached, so it would serve the image's original versions forever. `postCreate` runs on every container create, so a rebuild picks up the current release of each. The install is `|| true`: a registry failure must not fail container creation, and the version report below it prints `MISSING` if that happens. **Deliberately not pinned** — re-run the `verify-guild-*.sh` proofs after an opencode bump that matters.
- Auth is **in-container login**, persisted across rebuilds by **host bind mounts** under `~/.modelguild/` — `claude` → `~/.claude`, `opencode` → `~/.local/share/opencode`, `gh` → `~/.config/gh`. Log in once: `claude` → `/login`, and `opencode auth login`.
  - **All three were named Docker volumes (`modelguild-claude`/`-opencode`/`-gh`) until 2026-07-25.** A named volume survives `Rebuild Container`, but **not** `docker volume prune` / `docker system prune --volumes` / Docker Desktop "Clean / Purge data" / a `docker-desktop-data` reset — and when it goes, it silently takes every Claude Code session transcript in `~/.claude/projects/` and every OAuth token with it. That happened (maintainer, 2026-07-25: whole `~/.claude` re-created, re-login forced, `/resume` empty). A host directory survives all of it and can be backed up. **Cost of the change:** the state is now visible in the host filesystem rather than inside Docker's storage, and a host with a uid other than 1000 relies on `postCreate.sh`'s defensive `chown` rather than on Docker seeding the volume node-owned.
- **This is NOT a reversal of the abandoned host-credential mount.** That decision stands: mounting an *existing host secret* in fails on macOS, where a mode-600/root-owned file is unreadable by the non-root `node` user through the mount. Here the container **writes its own** credentials into an initially-empty host dir it owns — no host secret is read.
- **Bind sources are created by `prepare-host-state.sh` on the host** (chained into `initializeCommand` after `prepare-host-config.sh`), mode 700, honouring `MODELGUILD_HOST_STATE`. This is load-bearing, not tidiness: Docker creates a **missing** bind source **root-owned**, which the non-root `node` user cannot write. The `Dockerfile`'s `mkdir`+`chown` still pre-creates the mountpoints; `postCreate.sh` still chowns defensively (for a host uid ≠ 1000), keeps the surviving shell executable, and reports login status on each create.
  - A rebuild stops mounting the old named volumes but does not delete them. `prepare-host-state.sh` prints a `docker run … cp -a` recovery command when a state dir is empty and the matching volume still exists; it never copies on its own.
- **`gh` CLI** is installed via a dev-container Feature; its auth persists in `~/.modelguild/gh` (`gh auth login` once).
- **Both agents' VS Code extensions are installed** (`customizations.vscode.extensions`): `anthropic.claude-code` and `sst-dev.opencode` — the official opencode extension (publisher SST, source `github.com/sst/opencode`, the same repo the CLI ships from), so the editor surface matches the two CLIs `postCreate.sh` installs. Extensions are a VS Code-client concern only — nothing in `src/`, the lints or the `verify-*.sh` proofs reads them, so this changes no behaviour under test.
- **`postCreate.sh` runs `npm ci`** (issue #25) — `npm test`, `npx tsc --noEmit` and `npm start` need `tsx`/`typescript` from `devDependencies`, and nothing installed them before. It then reports every tool the documented workflows invoke, plus `node_modules`, timezone, and auth status, ending in a `!! missing tooling:` summary. **Deliberately non-fatal:** a registry hiccup must not fail container creation, so a gap is reported, not thrown. Nothing here sets a git identity — `postCreate.sh` only reports whether one exists.
- **Host config import:** before container creation, `prepare-host-config.sh` copies only `~/.claude/{CLAUDE.md,settings.json,statusline-command.sh,commands/,agents/}` into git-ignored `.devcontainer/.host-config`. The selected top-level files are dereferenced wherever they point (a dotfiles-managed `~/.claude` symlinks them to `~/.dotfiles`); symlinks discovered while walking `commands/`/`agents/` are confined to `~/.claude`, and dangling/non-regular entries (FIFOs, sockets, devices) are rejected. `postCreate.sh` links that snapshot into the active `~/.claude`. Covered by `.devcontainer/test-prepare-host-config.sh`.
- **The container adopts the host timezone** (issue #26); the image is UTC. `prepare-host-timezone.sh` (host-side, third in `initializeCommand`) probes `$MODELGUILD_TZ` → `$TZ` → the `/etc/localtime` symlink (cut at `zoneinfo/`, covering both the Linux and macOS zoneinfo roots without GNU `readlink -f`) → `/etc/timezone`, writes the zone to git-ignored `.devcontainer/.host-timezone`, and `postCreate.sh` applies it. **`"TZ": "${localEnv:TZ}"` was rejected:** `TZ` is unset on most desktops, so it expands to empty and the container silently stays UTC. The zone is validated at **both** ends (no dots, no leading slash) because it resolves as a path under `/usr/share/zoneinfo`; anything else is refused and any stale value cleared, so an undetectable host just stays UTC. Covered by `.devcontainer/test-prepare-host-timezone.sh` (CI, both platforms).
- **Login persistence gotcha:** Claude Code splits state between `~/.claude/` (the bind mount, persists) and `~/.claude.json` (in `$HOME`, ephemeral). `postCreate.sh` keeps the real file inside the mount (`~/.claude/home-dot-claude.json`) and symlinks `~/.claude.json` to it.
- **Session history has a second expiry beyond the mount:** Claude Code prunes transcripts in `~/.claude/projects/` older than `cleanupPeriodDays` (default 30). Persisting the directory does not make history permanent — raise that in `settings.json` if you want longer.

## Conventions

- **PARITY: asymmetry is DEFAULT-DENY, and every exception needs a named harness difference.** Do not restrict a non-Claude path more than the Claude path for the same task. This is a rule with a history: Claude did exactly this **three times in one day** (2026-07-15), each time inventing the restriction, then defending it to the maintainer in principled language, and each time being caught by the maintainer rather than by any test. **Loosening is the DEFAULT; the burden is on Claude to justify ANY restriction to the maintainer with a harness difference he accepts — not on the maintainer to fight each fence off** (the 2026-07-22 permission realignment).
  - **Clean-worktree guard** (`fc17389`): `/guild:delegate` refused a dirty tree. An Anthropic subagent editing the same files gets no such gate. **Removed.**
  - **"The diff review is the trust boundary"**: framing a delegated model's output as something to be *contained*. You review a subagent's diff, and your own PR, for the same reason — it's review, not quarantine. **Reworded.**
  - **Egress ban, then the whole secret-glob/grep/glob fencing on the read paths**: denied because "read + egress = exfiltration channel" — which is precisely what Claude Code and its subagents do. It cost real capability and the guarantee was theatre anyway. **Removed** (2026-07-22 realignment).
  - **The forcing question, before you add ANY restriction to an opencode agent:** *would I impose this on an Anthropic subagent doing the same task?* If no, it is bias — remove it, or name a concrete **harness** difference.
  - **Harness differences are the only valid asymmetry.** Named difference **(reads egress to a third-party vendor; surfaced by a security scan, accepted 2026-07-22)**: a read on the external read paths (`guild-read`/`guild-research`) egresses to a third-party model provider, whereas a Claude subagent's read stays inside Anthropic — so with the secret-glob fences removed, a credential these agents read can leave the host. This is **not fenced**: accepted as an informed trusted-repo tradeoff, documented in SECURITY.md. *(The former `grep`/`glob` harness difference — "opencode grep bypasses `read:` secret globs" — was REMOVED in the same realignment: circular, biting only if you fence secrets, which the read-only role does not.)* Second named difference **(TS serve transport; ratified 2026-07-22, tamper-signaled)**: `opencode serve` scaffolds `.opencode/node_modules` in the project dir (`opencode run` did not), so the `guild_delegate` snapshot fingerprint **and, since issue #108, its staging** exclude it — gated on the `scaffoldChanged` tamper signal, because that dir is execution-carrying. `--auto` was considered and rejected as a difference: it is a **proven no-op** for the hardened agents. Adding to this list requires evidence and the **maintainer's** sign-off; Claude does not add to it mid-design.
  - **The approval bridge (issue #20 slice 4, shipped 2026-07-28) IS a restriction, so it carries the burden — and it is answered.** *Forcing question:* would I impose this on an Anthropic subagent doing the same task? **Yes, and Claude Code already does** — in its default permission mode a subagent's `Edit`/`Write`/`Bash` calls surface to the user for approval unless allowlisted. So per-call approval on the external write path is the *Claude path's own default*, and offering it is parity, not a fence. *Direction of the asymmetry, honestly:* with the knob **OFF** — the shipped default — the external write path is **less** gated than the Claude path under its usual settings; that runs in the **permissive** direction, which PARITY permits (default-deny governs *restrictions*). Turning it on reaches parity without exceeding it: the gated set is the set Claude Code gates. *No new harness difference is claimed*; `GUILD_APPROVE_EGRESS` leans on the already-ratified one (reads on the external read paths egress to a third-party vendor) and spends it on an **offered, opt-in** gate rather than a fence. *Capability cost, stated:* an armed run cannot complete unattended (the whole reason it is off), a timeout-rejected mid-sequence edit can leave a **partial** change set (still captured and recoverable), the model burns extra tokens retrying around a rejection, the wait is spent inside the same `GUILD_MESSAGE_TIMEOUT_MS` budget as the turn — and **it buys less than it looks like it buys**, because an approved `bash` is an approved shell. *Provenance:* the ask is the **maintainer's** (issue #20, day one); the tiers, `all`'s existence and the egress knob are his decisions of 2026-07-28; the never-emit-`allow`/never-widen invariants, the up-front refusal and the watcher-presence design are Claude's.
  - **The worktree read root (issue #96, shipped 2026-07-29) is a LOOSENING, and it still states its cost.** *Forcing question:* would I impose the old restriction on an Anthropic subagent doing the same task? **No** — a Claude review subagent reads a sibling worktree without ceremony, and the external path could not, so the asymmetry was pure harness accident (opencode's `external_directory` rule × the default-deny floor) rather than a considered fence. ## Gotchas / decisions

- **The MCP server is a persistent process, keyed to Claude Code's session.** It shuts down on stdin EOF / transport close, not signals (see `src/lifecycle.ts`). The old `ask.sh` stdin `</dev/null` hack — `opencode run` blocked on a non-TTY stdin pipe — is a **transport artifact of the retired wrapper**, obviated by the HTTP client; there is no stdin blocking in the serve path.
- **"Read-only" ≠ "safe" — the confidentiality saga (bash-era history, 2026-07-15).** A read-only agent that can still read secrets or reach the network is an exfiltration channel, not a safe boundary. The default-deny **allowlist** shape (over a denylist) was reached the hard way: the first `guild-read` set `read: allow *` (last-match-wins re-opened `.env`), then a per-tool denylist kept leaking (`patch`, then `grep` returning secret content, then `glob`), so it was flipped to `"*": deny` + re-allow. **Lesson kept:** prefer an allowlist floor over a denylist for any versioned tool surface. **Superseded in part (2026-07-22 realignment):** the secret-glob read-denies and the `grep`/`glob` denials on the *read* paths were removed as vendor-asymmetry bias — those paths are `read`+`grep`+`glob`+web (review-subagent parity) and are explicitly not confidentiality boundaries. **Superseded again for the write path (2026-07-29, issue #29):** `guild-build` carried the secret-glob list a while longer and no longer does — `bash` bypassed it, so it fenced nothing a determined model could not walk around. **No agent def now carries a secret-glob read-deny.** The `grep`/`glob`-bypass argument is kept as the *history* of how the allowlist was reached, not the current rule.
- No network firewall on the container (decided against — low threat for trusted repos + frontier models). The read paths reach the web by design and are not exfiltration boundaries. The write path (`guild-build`) denies `webfetch`/`websearch` but allows `bash`, so egress is only *tool-native*-blocked there (bash `curl` still works) — a real firewall would be the only egress-proofing, and there is none. Delegate on trusted repos, and review the diff.
- PAL/Zen-style MCP servers were intentionally **not** used — they need API keys, conflicting with the no-API-keys design. A local server fronting opencode inherits opencode's OAuth; the rejection was about keys, never about MCP itself.
- The server drives `opencode serve`'s HTTP API (session create/message/history/delete, `/agent`, `/config/providers`, `/global/health`). Capture reads the **full-history** endpoint (the incomplete sync response omits tool parts). If you bump opencode and these endpoints change, update `src/client.ts` / `src/lifecycle.ts` and this file together; re-run the `verify-guild-*.sh` proofs.

- **`bash modelguild/verify-guild-read.sh` / `verify-guild-build.sh` / `verify-guild-research.sh` `[--static]`** — the authoritative proofs that opencode's **resolved** permission config matches each agent's intended allowlist. They call `opencode` directly (no dependency on any retired bash), so they need a logged-in opencode and run **locally** after an opencode/agent-def bump — never in CI (credential-free). `--static` runs only the token-free resolved-config check + a known-key lint; without it, a runtime probe (write-attempt / edit-path) corroborates on a free model, reported INCONCLUSIVE (not PASS) if opencode can't run. `verify-guild-read`/`research` assert `"*": deny`, `read`/`grep`/`glob`/`webfetch`/`websearch` allowed, mutation/`task` denied, and **no** former secret-glob read-deny remains; `verify-guild-build` asserts edit/write/patch/bash **and `read`** allowed, everything else (`task`/`grep`/`glob`/`webfetch`/`websearch`) denied, and — since 2026-07-29 (issue #29) — that **no** secret-glob read-deny remains there either. - **`bash modelguild/verify-permission-surface.sh`** — same family, same workflow slot (local only, after an opencode bump; never CI), different question: it makes issue #93's "re-probe before migrating" **executable**. It spawns a serve (or uses `$GUILD_VERIFY_BASE_URL`) and, for each agent in `$GUILD_VERIFY_MATRIX` (default: the armable tiers — `guild-build:bash|edit|patch`, `guild-read:webfetch|websearch`), creates a gated session carrying `{permission,*,ask}` rules and a control session carrying none, then evaluates each permission on `POST /api/session/{id}/permission` `$GUILD_VERIFY_ROUNDS` times per session and judges whether the ruleset **changed** the answer. **Differential by necessity** — an `ask` from v2 can come from the agent def or a built-in rule — and it **refuses to conclude** in four shapes, each of which was a real route to a false green: the stored ruleset not structurally intact (a substring check passes a ruleset that *denies* bash and asks about `read`), a control that shows the agent never allowed the tool, both creates returning one session id (no control at all), and rounds that disagree within **either** session (an unstable sample is not a verdict — #93 records a real first-call instability). Covering all armable families is deliberate: a verdict from `bash` alone would generalize past its evidence, so the PIN-HOLDS banner names the pairs it actually evaluated. Exit 0 = pin holds (the expected result on 1.18.7, reported as a result rather than a failure), exit 7 = **ATTENTION, revisit #93**, exit 6 = INCONCLUSIVE, deliberately distinct so "could not check" never reads as "pin holds". It calls **no model**, so unlike the `verify-guild-*.sh` runtime probes it does not need a logged-in opencode. There is no `--static` mode — every question it asks is about the running serve.
