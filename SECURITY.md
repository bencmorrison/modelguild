# Security policy

ModelGuild lets Claude Code hand work to other LLMs through [opencode](https://opencode.ai). This document is the honest account of what it does and does **not** protect against. Read it before using `/guild:delegate` on anything you don't fully trust.

## Threat model

ModelGuild is built for **trusted repositories and frontier models reached through your own opencode auth**. It is a collaboration tool with real, verifiable guardrails — **not a security sandbox**. It does not contain a hostile model, and it is not designed to run untrusted code safely.

- **No API keys are stored or managed by this repo.** Model access and auth live entirely in opencode (OAuth / your provider logins, including free-tier providers). Nothing here reads or writes your credentials.
- **The dev container has no network firewall** (a deliberate choice for trusted repos + frontier models). Egress is limited at the *tool* layer where noted below, not at the network layer.

## What is guaranteed, and how

The three agents ModelGuild defines are **default-deny allowlists** at opencode's permission layer: the permission map sets `"*": deny` (overriding opencode's built-in `"*": allow`, which opencode resolves last-match-wins), then re-allows only what each role needs. A denied tool is removed from the model's toolset — this is enforcement, not a prompt asking the model to behave. Because the allowlists leave nothing in an `ask` state, `--auto` cannot approve a `deny` into existence (it is a no-op for these agents).

**That whole guarantee is conditional on opencode being able to PARSE the def, and until issue #111 nothing at runtime checked whether it could.** Frontmatter opencode cannot parse is applied in **no part** — not partially, not with a warning, not with a non-zero exit. The permission map is absent entirely, the agent resolves on opencode's built-in `"*": allow`, and the file on disk still reads as hardened. Probed on opencode 1.18.7 (2026-07-29, live `opencode serve` + `GET /agent`, corroborated by `opencode agent list`): a control `guild-read` resolves ending `…, "*": deny, read: allow, grep: allow, glob: allow, webfetch: allow, websearch: allow`, while the same def carrying **one** duplicate key — at the top level *or* nested inside the permission map — or **one tab-indented line** resolves to opencode's built-ins alone, with no `"*": deny` anywhere. `mode` falls back to `all` in both cases, so there is not even a mode tell; `description` comes back `null`. Duplicate keys and tabs are the shapes currently known and are **not a closed list** — the condition is the parse. The realistic way in is not a hand edit: it is a merge conflict resolved by keeping both sides, and `modelguild init`'s never-clobber rule means a user-edited def then stays exactly as edited, forever, unlinted.

**What now stands between you and that: a two-stage check, and neither stage is a presence test of the floor.** Stage one is unchanged — the def **file** must exist in a dir opencode resolves from, or the tool refuses (`agent-def-missing`). Stage two (issue #111, CONTRACT C73) asks opencode, before the model turn, what it **actually resolved** for that agent (`GET /agent`) and computes the effective action — last match wins, the way opencode resolves it — for a probe tool no hardened def grants. Anything but `deny` is a refusal (`agent-unhardened`) that names the agent and what was resolved; nothing is routed and no evidence run is written. It is deliberately an *effective-action* test rather than "a `"*": deny` entry exists", so a later `"*": allow` re-opening everything is caught too. **The honest bounds:** the check is authoritative about the resolved config and says nothing about opencode's enforcement of it; it is per serve child (opencode resolves agents from the serve's cwd), and the cache behind it retains only a *verified* verdict, keyed on the child instance rather than its reusable loopback port — so a failure is re-checked every call and a dead child's verdict is never inherited. **Retaining a verified verdict for one child is sound rather than a risk, and for a reason worth knowing:** a running `opencode serve` child never re-reads an agent def — probed on 1.18.7, neither for the resolved config **nor for enforcement** (a serve started on `bash: allow`, with `bash: deny` swapped in on disk, still ran `bash` in a real turn) — so the check and the enforcement read one spawn-time config and cannot disagree. **The same fact breaks the obvious recovery, so read the refusal's remedy:** fixing the def and re-running `init` does **not** clear an `agent-unhardened` refusal, because the stale child keeps serving the old config, and every retry re-arms its idle timer. A fresh child is required — restart the MCP server, or stop calling until the serve idles out (`GUILD_SERVE_IDLE_MS`, default 600s); and **when opencode cannot be asked at all** — the control-plane call fails, or answers a shape the check cannot read — the call **proceeds** and says so, on the tool result (`structuredContent.agentUnverified`) and on stderr. That direction is deliberate: failing closed there would turn a transient into an outage on a check that verifies a control opencode still enforces, and the state it leaves you in is the pre-#111 status quo, now labelled rather than silent. **One consequence of proceeding is sharper than the rest and is stated in the note itself: if the approval bridge is armed (`GUILD_APPROVE` / `GUILD_APPROVE_EGRESS`), its gating may be NARROWER than the set of tools opencode will actually run.** The bridge decides what to gate by parsing the def **source**, so on a def opencode is not applying, every tool the void newly permits runs ungated and unprompted while the run still reports itself armed. That is the failure mode this project names as the worst the approval feature can have, and an unverified check cannot rule it out.

### `guild-read` — read-only ROLE, **NOT a confidentiality boundary**
Used by `/guild:consult`, `/guild:panel`, `/guild:workshop`, `/guild:review`, `/guild:collaborate`. It grants exactly a Claude review subagent's tools: `read` + `grep` + `glob` + `webfetch`/`websearch`. Denied: all mutation (`bash`/`edit`/`write`/`patch`) and sub-agent spawning (`task`). **The no-write/no-`task` scoping is the read-only ROLE** — it is what makes "read-only" true, the same scoping you'd give a Claude reviewer — not a security floor. Because it's an allowlist, any tool a future opencode version adds is denied until explicitly allowed.

**This is NOT an exfiltration or credential boundary — do not read it as one.** An external model on this path can read **any repo file, including credentials** (`.env`, `*.key`/`*.pem`, `.ssh/**`, `.aws/**`, `.git-credentials`, `.npmrc`, `.git/config`, `terraform.tfvars`, …), search the tree with `grep`/`glob`, and **reach the network** — so a secret it reads can leave to the third-party model provider or a fetched host. **Run it only on repos whose contents AND secrets you'd accept a third-party LLM seeing.**

**Why the secret-glob denies and the `grep`/`glob` denials were removed (2026-07-22 realignment).** The earlier def carried an enumerated list of secret-path read-denies and denied `grep`/`glob`. Both were **vendor-asymmetry bias**: you would not fence a Claude review subagent out of `grep`, out of dotfiles, or off the web, so fencing this one was restricting a non-Claude path harder than the Claude path for the same task. The secret globs were already conceded to be a *list*, never a boundary (you cannot enumerate every file a secret might live in). The "opencode `grep` returns file content and walks the tree with `--hidden`, bypassing `read:` denies" harness difference was **circular** — it only bites if you are fencing secrets, which this role is not. So the fences came off; the allow-set is now review-subagent parity.

**The one genuine harness difference, surfaced by a security scan and accepted.** A Claude subagent's reads stay inside Anthropic; a read on this external path **egresses to a third-party vendor** (the model provider opencode reaches). That is a real asymmetry, and with the secret globs gone it means a credential this agent reads can leave the host. It was surfaced by a security scan and **accepted as an informed trusted-repo tradeoff** (maintainer, 2026-07-22) — the exposure was chosen with eyes open, not overlooked. It is documented here and in AGENTS.md's PARITY section, and it is why the scope is "trusted repos only".

**What the read root is, and what it now includes (issue #96, 2026-07-29).** These agents read whatever directory the `opencode serve` child was spawned from — opencode's own `external_directory` rule fences them inside it. Since #96 a read call may name a **git worktree of the same repository** (`worktree` on `guild_consult`/`guild_panel`/`guild_research`) and be served by a child rooted there, so a second model can review a branch before it merges. **This is a widening, stated as one:** everything above about credentials and web egress now applies to that worktree too — a secret that exists only on that branch can be read and can leave to the model provider. It is bounded in three ways and no further: the target must be an exact member of `git worktree list` for the repository the server already resolved (an arbitrary path, or a worktree of a **different** repository, is refused by name — never silently swapped for the project root); it is **opt-in per call**, so a call without a target behaves exactly as it did before; and (until issue #107) it was not offered on the write path at all — see **the write root** under `guild-build` below, where it now is, on terms that move the capture with the child. Two operational consequences worth knowing. Each distinct root in use is another `opencode serve` process and another loopback port (the surface documented below, multiplied). And opencode writes an `.opencode/node_modules` scaffold into a targeted worktree that already contains an `.opencode/` directory — **git-invisible only when opencode wrote the ignore file itself**: it creates `.opencode/.gitignore` covering what it adds, but does **not** overwrite an existing one, so a repo that commits its own `.opencode/.gitignore` sees `?? .opencode/node_modules/`, `?? .opencode/package.json` and `?? .opencode/package-lock.json` after a read-only review — a `/guild:review` visibly mutating the tree under review, and a later `git add -A` there would commit opencode's `node_modules`. Nothing in the code prevents this; it is stated so you can expect it. A **continuation** (`sessionId`) does not widen anything further: its root comes from the session's own recorded directory, and a `worktree` that disagrees with it is refused rather than silently honoured. The read root a call used is recorded in the evidence log's `started` entry (`read_root`), so the receipts say which tree an answer describes. **Run it only on worktrees of a repository you would already accept a third-party LLM reading.**

This is verified two ways — run both after any opencode or agent-def change:
- `bash modelguild/verify-guild-read.sh` — asserts the **resolved** config (authoritative, needs opencode): the `"*"` floor is `deny`, mutation/escape tools (`bash`/`edit`/`write`/`patch`/`task`) resolve to deny, `read`/`grep`/`glob`/`webfetch`/`websearch` resolve to allow, and **no** former secret-glob read-deny remains; plus a runtime probe that a write attempt leaves no file.
- `bash modelguild/tests/check-agent-permissions.sh` — an opencode-free source lint (runs in CI) that checks the same allowlist invariants, frontmatter-bounded and last-match-aware.

### `guild-build` — the `/guild:delegate` write path: **defense-in-depth, NOT by construction**
Used by `/guild:delegate`: the `guild_delegate` MCP tool names the `guild-build` agent directly (`src/delegate.ts`) — there is no flag that selects it, and if the hardened def is not found the tool **refuses** with `agent-def-missing` rather than falling back to opencode's unrestricted `build` agent. It re-allows `edit`/`write`/`patch`/**`bash`** and `read`; everything else (sub-agents, `grep`/`glob`, network) is denied. **Because `bash` is allowed by design** (a coding task must run builds/tests), the remaining denies are *defense-in-depth* — they remove the tool-native routes a compliant model would default to, but a determined model can `curl`, grep, or even launch a fresh unrestricted `opencode --agent build` **via bash**.

**A guarantee this document used to state has been REMOVED (2026-07-29, maintainer decision, issue #29): `guild-build` no longer denies secret reads.** The def used to carve `.env`, `*.key`/`*.pem`, `.ssh`/`.aws`, `credentials*`, `.netrc` and `.git-credentials` out of its `read` tool, and the paragraph above used to list "secret reads" among what it denied. Those carve-outs are gone, and so is that claim. **Plainly: this removes a layer.** A *compliant* model that the tool layer would previously have refused now simply gets the bytes — the tool-native route to a credential file is open where it was closed. What has not changed is that the fence never bound a *determined* model: `bash` is allowed on this agent by design and `cat .env` walked straight through it, as the def and this document already said. It was defense-in-depth over a boundary that did not exist, and it implied one — "secret reads denied" reads like a credential guarantee, on the one path that has a shell. It was also the last survivor of a list the read paths dropped on 2026-07-22.

So, without hedging: **`guild-build` can read any file in your repository, credentials included** — via the `read` tool now, and via `bash` all along. Delegate only on repos whose contents **and secrets** you would accept a third-party model seeing, the same condition already stated for `guild-read`/`guild-research`. Nothing here makes `/guild:delegate` safer; it makes the permission map an honest description of it, and the human diff review is the boundary it always was.

On this path, **the trust boundary is you reviewing the diff**, not the permission map. To support that:
- The `guild_delegate` tool **snapshots your worktree** before the write agent runs (a git tree, via a throwaway index — your files and staged state are untouched) and records the model's diff at `modelguild/logs/<run_id>/diff-<call_id>.patch` (returned as `structuredContent.capture.patchPath`). Two consequences worth knowing: the patch is the model's changes **only**, even if you had uncommitted work in progress; and anything of yours the model overwrites is **recoverable** (`git checkout <tree> -- <path>`, in `capture.recoveryHint`). There is deliberately **no clean-worktree requirement** — delegating onto live work is the point, and a snapshot serves it better than a refusal did.
- **The recorded patch is not guaranteed to be complete, or to exist — read `capture.captureComplete` and `capture.incompleteReason` before you treat it as the whole story.** Capture is marked incomplete when the state cannot be faithfully represented (`baseline-tree-unavailable`, `after-tree-unavailable`, `ignored-state-incomplete`, `ignored-paths-changed`, `submodule-worktree-unrepresentable`, `diff-generation-failed`) or when the capture itself crashed (`capture-crashed`); the `delegate-diff` entry then records `complete:false`, so the run **fails** evidence-log integrity loudly rather than passing as a full record. On `capture-crashed` there is **no patch the entry can vouch for** — a half-written `diff-<call_id>.patch` may well be sitting in the run dir, but nothing hashed it, so the entry names the reason and claims no artifact rather than pointing at bytes it cannot stand behind. It is still written, and it is still what fails the run (fixed 2026-07-28, issue #74: the crash path previously wrote **no** entry, so a run whose capture died verified *clean* and looked exactly like a delegation that changed nothing). **One residual, stated because it is invisible in the log:** if the evidence write *itself* fails (a lock timeout, or ENOSPC — which is exactly the sort of condition that crashed the capture in the first place), no entry lands and the run verifies clean again. Nothing in `calls.jsonl` can show you that; `capture.recordFailed` on the tool result is the only witness, and when it is true you should treat the worktree as unrecorded. `capture.patchPath` is `null` when the target is not a git worktree (no snapshot, no diff recorded), when the model changed no tracked files ("nothing to review"), and when the capture crashed. The snapshot is a **record, not containment** — an incomplete or absent capture means your diff review is working from less than the model did, so treat it as a reason to inspect the worktree yourself, not as an all-clear.
- **Review the recorded patch, not `git diff <sha>`** — a plain diff does not show files the model *created*, so a delegation that only adds files looks like it changed nothing. The patch is built from tree snapshots and includes created files.
- `/guild:delegate` instructs Claude to review the diff (and scan it for injected or out-of-scope changes) before anything is trusted or committed.

**The write root (issue #107, 2026-07-29) — the same widening, on the path that can CHANGE things.** `guild_delegate` now accepts the same `worktree` argument as the read tools, validated at the same choke point (exact membership of `git worktree list` for the repository the server already resolved; anything else, a worktree of a *different* repository included, is refused by name — never a silent edit of the project root), so a delegated model can edit files **and run `bash`** in a sibling worktree. **Stated without hedging: everything this section says about `guild-build` now applies to that tree** — it can read any file there including credentials, and `bash` reaches the network whatever the tool-layer denies say. It is enumerable, it belongs to the repository you are already working in, and it is opt-in per call (a call with no target behaves exactly as before), but it widens what can be **changed**, not merely what can be read.

**The property that makes the diff review survive this is that the capture moved with the child, and it is worth understanding why it is stated as a security property.** The trust boundary above is *you reviewing the diff*; that boundary only exists if the diff is of the tree that was actually edited. Re-rooting the serve child while leaving the snapshot, the baseline/after trees, the ignored-file fingerprint, the scaffold tamper digest, the recovery hint and the recorded patch at the project directory would have produced a patch describing the **wrong tree** while reporting `captureComplete:true` — a failure that reads exactly like success. So one root is resolved per call and shared by both, `structuredContent.worktree` names the tree that was edited, the evidence log's `started` entry records it as **`write_root`** (its own field: "this tree was mutated" is a different claim from `read_root`'s "the answer describes this tree"), and the recovery hint comes back as `git -C <worktree> checkout <tree> -- <path>` — because a worktree shares its main checkout's object database, so the bare form pasted in the wrong tree restores *successfully* into the wrong tree. A worktree that does not carry the hardened `guild-build` def refuses up front, naming that worktree's own agent dir, rather than falling back to opencode's unrestricted `build`.

**Expect the plugin scaffold, and read the tamper warning's wording.** opencode materializes `.opencode/node_modules` + its manifests into any serve cwd that already contains an `.opencode/` directory (probed on 1.18.7, 2026-07-29: an *empty* `.opencode/` is enough; a directory with none is never scaffolded), on the first request that loads its plugin runtime rather than at serve start. The **first** delegation into a freshly added worktree that carries `.opencode/` will therefore trip `capture.scaffoldChanged`. **That flag always fires** — a tamper signal that goes quiet because a benign explanation exists is worthless — and `capture.scaffoldWarning` is what varies, on a precondition that is **recorded at baseline, not assumed**. Read it, because the three cases mean different things:

- an **existing** plugin directory was *modified* — no benign explanation, review it;
- scaffolding **appeared** in a tree that already had `.opencode/` — opencode's own first-run materialization is a *sufficient* explanation, and the warning says so without claiming it is the *whole* explanation, because a single digest cannot separate opencode's scaffolding from something written alongside it;
- scaffolding was **created** in a tree that had **no** `.opencode/` beforehand — opencode does **not** scaffold such a tree, so this is an **unexplained** write into a directory `opencode serve` loads and executes, and it is reported as such.

The third case is reachable and is why the precondition is checked rather than inferred: under an `init --global` install the hardened def resolves from `${XDG_CONFIG_HOME:-~/.config}/opencode/agent`, so a target worktree can carry no `.opencode/` at all and still pass the def pre-check. An earlier cut of this feature inferred that delegation always implies `.opencode/` and would have handed that case the reassuring wording.

**The scaffold is not in the recorded patch, and that is deliberate — the warning is where it surfaces (issue #108, 2026-07-29).** The snapshot stages with `git add -A`, which honours `.gitignore`, so the scaffolding stayed out of the patch only because opencode had written an `.opencode/.gitignore` covering it — and opencode **does not overwrite an existing one**, so a repo that commits its own used to get thousands of `node_modules` paths in `diff-<call_id>.patch`, on the first delegation into each not-yet-materialized tree. The staging now drops the same `.opencode/node_modules/**` + manifest set the ignored-file fingerprint already excluded, **wherever the repository does not track those paths** (a manifest you commit on purpose stays in the diff like any other tracked file), with the tracked set fixed at the pre-turn baseline so a model that runs `git commit` mid-turn cannot flip a path between the two trees. **That exclusion, not any ordering, is what makes this hold — because it is timing-independent.** It strips the untracked scaffolding from the index of *both* snapshots, so those paths are in **neither** tree no matter when opencode writes them; nothing about it depends on whether the runtime was materialized before the baseline, between the snapshots, or during the turn. (Worth stating because a second feature now contacts opencode before the turn — see the resolved-agent check below — and it changes *when* the scaffolding appears without changing this guarantee at all.)

**Read the consequence plainly, because it is sharper than "one fewer path in the diff".** A write into that untracked directory is invisible in the patch in *every* repo now, where one ignore-file configuration used to show it by accident — and `opencode serve` **loads and executes** that directory. `capture.scaffoldChanged` and its warning are the only remaining surface, which is why they are never suppressed — **and keeping them MEANINGFUL took an ordering fix once a second feature started contacting opencode before the turn** (issue #111, 2026-07-30). The resolved-agent check issues `GET /agent`, which writes `.opencode/.gitignore` synchronously (the rest of the runtime lands hundreds of ms to seconds later, measured). That one file is enough to make a post-check baseline non-empty, which would have selected the severe *"plugin directory modified — no benign explanation"* wording on **every** first delegation into a tree — a false alarm on a routine event, which is how a signal like this stops being read. The scaffold digest is therefore captured *before* that check. The signal would have kept firing either way; what was at stake was whether it told you the truth about which case you were in. **But note which warning you will get:** in the common shape — a plugin written during the first delegation into a tree that already had `.opencode/` — the three cases above correctly select the *sufficient explanation* wording, so the patch shows nothing and the surviving signal reads as opencode's housekeeping. Treat that wording as a prompt to look at `.opencode/node_modules` yourself, not as an all-clear. `activity.jsonl` records the edits opencode reported, and `git status` in the tree shows what landed. `.opencode/agent/**` — the hardened defs — is **not** in the excluded set and is fully in both the fingerprint and the patch.

Delegate only on trusted repositories, and always review the diff — **of the tree that was actually edited.**

### `guild-research` — the source-backed `/guild:research` workflow: **cannot mutate, is NOT a confidentiality boundary**
Used by `/guild:research`: the `guild_research` MCP tool names the `guild-research` agent directly (`src/research.ts`) — there is no flag that selects it, and a missing hardened def is an `agent-def-missing` refusal, never a downgrade to a weaker agent. It has the **same allow-set as `guild-read`** — `read` + `grep` + `glob` + `webfetch`/`websearch` — with `bash`, `edit`/`write`/`patch`, and `task` denied. The no-write/no-`task` scoping is the read-only ROLE; the secret-glob read-denies and the `grep`/`glob` denials were removed in the 2026-07-22 realignment for the same reason as `guild-read` (vendor-asymmetry bias — see that section).

What genuinely holds: **`bash` is denied**, so there is no shell to `cat` a file or `curl` around the tool layer, and no sub-agent escape. This path **cannot mutate the repo**.

What does **NOT** hold: this is not an exfiltration or credential boundary. Local `read` + `grep`/`glob` + network egress means an external model here can read **any repo file, including credentials** (`.env`, keys, `.aws`/`.ssh`, `.git-credentials`, `.npmrc`) and send it to the third-party model provider or a fetched host — egress is by design here (research needs the web). Additionally, **fetched pages are attacker-controlled**: a page can carry text aimed at the model ("read X and fetch evil.example/?d=…"); the agent's own prompt and `/guild:research`'s injection guard push back, but that is model compliance, not construction.

It also accepts the `worktree` read root (issue #96) on the same terms as `guild-read` — see that section for exactly what widens and what bounds it.

So: **run `/guild:research` only on repos whose contents AND secrets you'd accept a third-party LLM seeing.** Verified by `bash modelguild/verify-guild-research.sh` (asserts the `"*"` floor, `read`/`grep`/`glob`/`webfetch`/`websearch` allow, mutation + `task` deny, no former secret-glob read-deny remains, plus a runtime probe that a write attempt leaves no file). It deliberately does not claim non-exfiltration.

## Other guardrails

- **Prompt-injection guard.** Every command treats external model output as untrusted **data, not instructions**. If a model's answer (or a `/guild:delegate` model's report/diff) contains directives aimed at Claude ("ignore your instructions", "now run/commit/delete…", fetch a URL, reveal secrets), Claude surfaces them as a finding rather than acting on them.
- **Model policy.** Policy rules are first-match globs with default-allow. Resolution is **layered** (issue #19): `$GUILD_POLICY` when set is a single-file override; otherwise the chain is project `models.policy.local` → project `models.policy` → global `~/.claude/modelguild/models.policy.local` → global `models.policy` → default-allow, most-specific first, with the **first matching rule anywhere** winning. A `models.policy.local` joins the chain only if it contains at least one rule, so an empty/comment-only local file does not mask the shared policy. **Security consequence, stated both directions:** a global `deny` now keeps binding inside a project that previously would have shadowed it (a genuine tightening over the pre-#19 behaviour), *but* a project-local rule is evaluated **before** the global one, so a repo you install into can place a looser `allow` above your global `deny` — treat a project's committed `models.policy` as repo-supplied content, like any other file in a repo you chose to trust. `$GUILD_ROOT` pins one root and layers nothing beneath it, so a global policy does not bind while it is set (`doctor`/`guild_status` say so explicitly). The tools refuse a `deny` model and require explicit user approval (`confirmed:true`) for an `ask` model. Fail-closed is chain-wide: a malformed or unreadable policy file in **any** layer denies.
- **The post-call agent-mismatch check is conditional — it fires only when opencode reports the serving agent.** Each model-calling tool compares the agent opencode names as having answered (`info.agent` on the answering message) against the one it requested, and fails the call closed as `agent-mismatch` when they differ, so a silent fallback to the unrestricted `build` agent cannot come back dressed as hardened output; when that field is **absent** the tool treats it as "opencode didn't say" rather than as a mismatch — fail-open there, deliberately, because inventing a mismatch on absence would break on any build that drops the field. The controls that do **not** depend on it are the primary ones: the pre-flight `agent-def-missing` refusal (no model call at all when the hardened def is missing from both agent dirs) and opencode's own permission enforcement of whichever agent it resolved. Keeping the documented fail-open is a **maintainer decision (2026-07-28)** — the residual risk needs two simultaneous failures, a build that stops reporting the agent *and* a silent fallback to an unrestricted agent.
- **Preflight.** `npx modelguild doctor` checks the MCP registration, the policy, the installed payload (including upgrade drift), and that the `opencode` binary is on PATH and reports a version, before you rely on the commands. It is **token-free and does not check auth**: it never logs in, never queries a provider, and cannot tell you whether your opencode session is still valid — an unauthenticated setup passes `doctor` and fails at the first model call. Confirm auth with `opencode auth login` yourself. The resolved-config permission proofs (`verify-guild-*.sh`) are run locally after an opencode bump.

### `modelguild/logs/` — the evidence layer holds prompts, on disk, in your repo

`src/log.ts` records every model call to a git-ignored `modelguild/logs/<run_id>/calls.jsonl`. Each call writes `expected-call`, `started`, and `completed` entries with one `call_id`; verification requires exact lifecycle cardinality and validates capture state, artifacts, and every entry's hashes. By default (`GUILD_LOG_PROMPTS=full`) that includes **the full prompt Claude sent**. Responses are always recorded in full.

- **These are receipts** — the other model's actual words, on disk and yours to read, so you can check Claude's account of an exchange against what was really said. It is git-ignored, never transmitted, and pruned after 14 days (`GUILD_LOG_RETENTION_DAYS`) — enforced when the MCP server starts, at each new run, and on demand with `npx modelguild logs clean`; `GUILD_LOG=off` stops the automatic pruning too, so turning logging off does not quietly delete what is already there. It is a *local file*, not a network surface — but it is a plaintext copy of repo context living outside the files it came from, and it will be caught by anything that archives or backs up your working tree.
- **Set `GUILD_LOG_PROMPTS=hash`** (digest only — proves the prompt didn't change, reveals none of it) **or `off`**, in `modelguild/modelguild.conf.local`, if that copy isn't acceptable for your work. `GUILD_LOG=off` disables the log entirely.
- **The hashes are not tamper-proofing.** `prev_hash` chains entries and each entry carries a self-hash; referenced patch artifacts are checked too. This catches accidental corruption across generic entry types but provides no chain of custody: anything that can write the log can rewrite the hashes.
- **The record is best-effort, so it can have a gap.** Appends are serialized by a lock, and under sustained contention (~10 s) the entry is **dropped** rather than risking a torn concurrent append — a bounded gap is still readable evidence, a torn line poisons the record around it. Logging never fails the call it records, so the drop warns on stderr and the call proceeds; it is **`verify`**, not the write path, that surfaces the missing entry afterwards.

### The loopback `opencode serve` surface

The MCP server is the shipped implementation (the bash `opencode run` wrapper it replaced is retired). One new network surface comes with it:

- **The MCP server spawns `opencode serve`, which listens on `127.0.0.1` on an ephemeral (OS-chosen) port for as long as the server is up.** The retired `opencode run` path spawned a one-shot process with **no** listening socket, so nothing local could reach it.
- **During that window, any process on the host can reach the serve API** — it is plaintext HTTP and, by default, unauthenticated (opencode prints an unsecured-server warning; `OPENCODE_SERVER_PASSWORD` exists if you need auth). The permission map — not the transport — is what still enforces read-only per agent.
- **Mitigations, all implemented in M1:** the socket binds **loopback only** (never a routable interface); an **idle timeout** (`GUILD_SERVE_IDLE_MS`, default 10 min) kills the serve after inactivity so the window is not open indefinitely; an **optional per-call spawn mode** (`GUILD_SERVE_PER_CALL=1`) opens the socket only for the duration of a single call; and **shutdown-on-stdin-EOF / transport-close** tears the serve down the moment Claude Code closes the connection, closing the window at session end rather than orphaning a listener.
- This is an **accepted, documented surface** — the trade for the MCP transport that replaces the per-command grant matrix (the MCP transport rewrite; see AGENTS.md Architecture). It is in scope for the threat model to the same extent as the rest of the loopback tooling.
- **The approval bridge adds a reply path on that same port, and it can UN-BLOCK a gated tool (issue #20 slice 4).** When `GUILD_APPROVE`/`GUILD_APPROVE_EGRESS` is armed, a gated tool call waits on `POST /session/{id}/permissions/{permId}` or `POST /permission/{id}/reply`. Those endpoints are part of the same unauthenticated loopback API — so **anything on the host that can reach the serve port can approve a tool call you were asked about**, exactly as it could already drive the session API directly. This does not widen the surface (a process that can reach the port could already create its own session and run the `build` agent); it does mean **the approval prompt is not an authentication boundary**: it tells you what is about to happen, it does not prove the "yes" came from you. `OPENCODE_SERVER_PASSWORD` is the only thing that would change that, and this project does not set it.
- **What the approval prompt is, precisely.** It is attention and an interrupt. **Approving a `bash` call approves a shell**: that command can read any file including your credentials, reach the network, and spawn processes that raise no further prompts. Approving an `edit` shows you a path, not the content that will be written. The **human diff review** (`/guild:delegate` step 3) remains the write path's review point, and nothing in this feature changes the trusted-repo posture. It is off by default; it is not a sandbox, a containment mechanism, or a confidentiality boundary.
- **Fail-closed, and refused rather than armed blind.** An unanswered request is rejected after `GUILD_APPROVE_TIMEOUT_MS`. If the bridge is armed and nothing can answer (no MCP elicitation capability, no live `modelguild watch --approve`), the tool **refuses the call up front** instead of arming — because an unanswered `ask` under `opencode serve` hangs the turn rather than failing closed. The bridge emits **only `ask` rules**, and only for tools the agent's def already allows, asserted at construction and again at the wire: a session ruleset merges over the agent def and can override in both directions, so a single `allow` line would hand a shell to the read-only agent.
- **The blind window: narrowed to the reconnect, not closed (issues #77, #91).** The bridge answers requests off opencode's event stream. If that stream drops while armed, every request still **open** is rejected immediately and the result reports `approval.degraded` with a reason. A request the model raises **while the bridge is blind** is not in the reconnected stream either — SSE has no replay — so it used to be never prompted and never rejected on the approval clock, waiting on `GUILD_MESSAGE_TIMEOUT_MS` (default 15 minutes) instead of `GUILD_APPROVE_TIMEOUT_MS` (default 120 seconds). **On re-attach the bridge now asks opencode what is still open and puts those requests to you**, so the window in which a request can go unnoticed is the reconnect backoff (seconds) rather than the turn's backstop (minutes), and its approval clock starts when it is seen. **This is "recovered on re-attach", not "never missed":** opencode lists what is still *open*, so a request raised **and answered by another channel** during the window leaves nothing to recover, and the counts for that window can under-report. That list is global to the serve child, so the bridge answers only requests belonging to **its own session** — on a panel, that filter is what keeps one member's bridge from deciding for another. A `GET /permission` that fails leaves the bridge degraded rather than failing the call. One case the re-list deliberately does **not** fix: if a reject the bridge sent never took effect and opencode is still holding that request, it is recorded and left alone rather than re-asked — a request you have already answered is never put back in front of you — so that one falls back to the turn's timeout. And this is the *approval* layer only: `activity.degraded` still latches for the whole call, because a hole in a trace does not heal on reconnect the way sight does. The gated call does not proceed through any of this — opencode holds it at the `ask` — so what the blind window costs is a **stall**, not a tool that runs without being offered to you, and losing the stream is deliberately still not grounds to kill the turn. Read `approval.degraded` as "the gate cannot see right now", never as "the model stopped asking"; it clears only on a clean re-list, and `blindWindows` stays set to tell you a window happened at all. Do not read "rejected after `GUILD_APPROVE_TIMEOUT_MS`" as a bound on anything the bridge never saw.
- **A decision that cannot be DELIVERED is detected, not absorbed (issue #97).** opencode answers 404 to a reply for a request it is no longer holding — which is how the first-reply-wins arbitration is observed, and also exactly how a **removed reply endpoint** would look. `POST /session/{id}/permissions/{permId}`, the endpoint that delivers an **approval**, is the only operation opencode 1.18.7 marks `deprecated`; if it goes, approvals fail while rejections keep landing — you say yes, nothing happens, and the turn stalls to the model-turn timeout. So **any non-2xx opencode answers** — not the 404 alone, since a removed route can equally give 405 (the path still matches the method table), 410 (retired) or 501 (proxied or rewritten) — is followed by one bounded `GET /permission` and classified from the answer: still open ⇒ **`unsettled`** (nobody's decision landed) with a reason that, for an approve-path refusal, names the deprecation, the status observed and the `verify-permission-surface.sh` re-probe — the most informative reason seen wins that field, so a weaker detection cannot hold it while the real diagnosis goes unreported; not open ⇒ `contested` for a 404 (the race, now one the bridge went and looked for) or `refused` for any other status (observed, undiagnosed — the race reading belongs to a 404); the check itself unable to answer ⇒ neither **claim** — still counted in whichever of those two the status selects, but recorded `still_open: null` rather than guessed. Each request holds exactly ONE of the four classifications, a later observation superseding an earlier weaker one, and a reply still **in flight** is none of them (`unsettled` also covers a reply opencode ACCEPTED that did not take effect, so it is not refusal-only). `undelivered` is now the transport arm alone — nothing came back, so opencode's state is genuinely unknown — which is what it always claimed and, until this change, was not: a 410 landed there under a note asserting the reply never reached opencode. **This is reporting, not containment** — nothing runs ungated in any of those cases (opencode holds the call at its `ask`); what is at stake is whether a systematic approval failure reaches you as a diagnosis or as a stall. Three deliberate bounds: it reads opencode's **v1** open-request list, so a request raised on a different permission surface reads as *absent* and is not detected by this counter (CONTRACT C69a's pin, not this check, is what guards that); on a **panel**, one sibling member's protocol-violating open-request entry downgrades the check to unconfirmed for every member, narrowly re-enabling the absorption this exists to remove — accepted, because the alternative is answering "gone" about a request that might be sitting in that very entry; and a confirmed-undelivered approval is **never** retried as a rejection down the endpoint that still works, because unsticking the turn that way would convert consent you gave into a refusal you did not.
- **The ask-tier gate is instruction-layer + audit trail, not a forced prompt.** An `ask`-policy model returns a structured error telling the driver the human must approve, and the tool mechanically refuses to proceed without `confirmed:true`; each `started`/`completed` evidence entry records `tier`/`confirmed`. But the MCP surface has **no per-argument permission gate**, so `confirmed:true` cannot be made to *force* a user prompt — a driver that sets it without asking is caught **only by after-the-fact reading of the receipts, not prevented**. Do not claim otherwise. (The `confirmed` field carries the USER's approval; Claude must obtain it by asking, never grant it itself.)
- `GUILD_TEARDOWN_MODE=spike` is a **test-only seam**: it drops the primary stdin-EOF watch so the flagship orphan test can demonstrate the orphan bug against the spike's own (weaker) approach. It must never be set in production; worst case is the orphaned-serve regression the primary teardown exists to fix — an availability issue, not a security hole.

## Reporting a vulnerability

Please report security issues **privately**, not in a public issue:

- Preferred: open a private vulnerability report via GitHub → the repository's **Security** tab → **Report a vulnerability**.

Include what you found, how to reproduce it, and the impact. Because this is a small project, expect an acknowledgement on a best-effort basis. Fixes to the permission model ship with an updated `verify-*.sh` / `check-agent-permissions.sh` assertion so the same hole can't silently return.

## Scope notes

In scope: the permission model and its enforcement, the tools' guards (worktree snapshot, policy, injection), any way to make a read-only command (`guild-read`/`guild-research`) **mutate the repo, shell out, or spawn a sub-agent**, and any way to make `guild-build` exceed "edit + bash on a trusted repo you're reviewing". (Reading repo contents **including credentials** and reaching the web from the read paths is the documented, accepted trusted-repo tradeoff of the 2026-07-22 realignment — not a vulnerability; the same applies to a **git worktree of the same repository** named via the `worktree` input, which is the accepted widening of issue #96. Exfiltration of any repo data via read+web agents is likewise accepted. `guild-build` reading a credential file **through its `read` tool** is likewise accepted and not a vulnerability: the carve-outs were removed on 2026-07-29, issue #29, and `bash` bypassed them before that.) Out of scope: opencode itself, the models, your provider auth, and running untrusted code (ModelGuild is not a sandbox).
