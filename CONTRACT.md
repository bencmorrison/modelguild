TypeScript/MCP rewrite could be verified against it. **The rewrite is complete and the bash layer
retired at M12 (2026-07-23).** These C-items are no longer a bash-parity target — they are the
**behavioral specification the TypeScript implementation holds**, now verified by the TS test suite
under `test/` (the reference).

## A. Model policy semantics
*Oracle: `modelguild/ask.sh` (`_has_rules`, `policy_tier`, policy enforcement block); `run-tests.sh` cases 11, 12, 20, 20b, 20c; `modelguild/models.policy`.*

- **C1** (amended 2026-07-25, issue #19 — resolution is now **LAYERED**) — Policy resolution walks an ordered chain of files, **most-specific first**, and the **first matching rule anywhere in the chain wins**: project `modelguild/models.policy.local` → project `modelguild/models.policy` → global `~/.claude/modelguild/models.policy.local` → global `~/.claude/modelguild/models.policy` → default-allow. A `models.policy.local` joins the chain **only if it has ≥1 complete rule** (the `_has_rules` gate is kept). `$GUILD_POLICY` is a **single-FILE override**: when set it is the entire chain, with nothing layered beneath it. The pre-#19 behaviour — one root wins and its single file is the whole policy, so a project `modelguild/` shadowed the global one entirely — is **superseded**: the global install is the **baseline** and the project adds a stricter deny or a looser allow on top of it. (`resolvePolicyLayers` / `policyTierAcross` in `src/policy.ts`; `policyTier` remains the single-root view.)
- **C2** (amended 2026-07-25, issue #19) — An empty or comment-only `.local` (a `deny` with no pattern is not a rule) does **not** shadow the committed policy: it is excluded from the chain entirely, so it neither displaces a committed rule nor fails the chain closed as a malformed layer. A **ruleful** `.local` no longer *replaces* the committed file either — it sits **above** it, so a personal rule wins for the ids it names while committed rules keep binding for the ids it does not.
- **C2b** (new 2026-07-25, issue #19) — Fail-closed is **chain-wide**: every existing layer is parsed even after a rule has matched (as C6 already requires within one file), so a malformed active line or an existing-but-unreadable file in **any** consulted layer resolves to **deny** with the loud reason naming that file. Stated cost: a broken *global* policy denies in every project, not only in the global one — the fail-closed direction, with the offending file and line named.
- **C3** — Tiers are `deny` / `ask` / `allow`. Patterns are shell globs matched against the full `provider/model` id. **First matching rule wins**, top to bottom.
- **C4** — Default is **allow**: no policy file, empty model id, or no matching rule all resolve to `allow` (policy only ever restricts).
- **C5** — Fail-closed: an existing-but-unreadable policy file resolves to **deny**.
- **C6** — Fail-closed: any malformed active line (unknown tier, missing pattern, trailing non-comment token) resolves to **deny** — even when `-m` was omitted, the whole file is still parsed. A final line lacking a trailing newline is still read.
- **C7** — A `deny` model exits **3** before opencode is invoked (no argv reaches opencode). An `ask` model without `GUILD_CONFIRMED=1` exits **4**; with it, proceeds. Enforced as a hard backstop independent of Claude's own check.

## B. Model & config resolution
*Oracle: `modelguild/ask.sh` (`conf_get`, model precedence); `modelguild/panel-models.sh`; `run-tests.sh` cases 2, 15, 21, 21b, 21c, 21d, 21e.*

- **C8** — Default-model precedence: `-m` flag > `$GUILD_MODEL` env > `modelguild.conf.local` `GUILD_MODEL` > opencode's own default (empty).
- **C9** (amended 2026-07-25, issue #19 — resolution is now **LAYERED**) — Config file resolution: `$GUILD_CONF` if set is a **single-FILE override** (the whole answer, nothing layered under it); otherwise **every** layer's git-ignored `modelguild.conf.local` contributes — the global `~/.claude/modelguild/` read first as the baseline, the project's `modelguild/` overlaid on top. A key set in the project **wins**; a key the project leaves unset **falls through** to global. The overlay is C10's last-assignment-wins applied to the concatenated layers, so there is one parser and no second merge rule (`resolveConfFiles` / `readLayeredConfContents` in `src/config.ts`). Parsed, **never sourced** (no code execution).
- **C9b** (new 2026-07-25, issue #19) — Guild-root resolution is layered: the read layers are `<cwd>/modelguild/` (when present) over `~/.claude/modelguild/` (when present), most-specific first. `$GUILD_ROOT` is a **single-root override** — exactly one layer, no global baseline beneath it — so an explicitly pinned root stays hermetic; `guild_status`/`doctor` report the roots on disk it leaves unlayered. The **primary** root (`layeredRoots()[0]`) is unchanged in meaning and is where **writes** go: the evidence log's `logs/` directory (`layeredRoots` / `resolveGuildRoot` in `src/config.ts`).
- **C10** — Config parsing: only `KEY=value` lines; comments/blanks ignored; leading whitespace on key stripped; last assignment wins; one layer of surrounding single/double quotes stripped; a trailing `  # comment` on the value is stripped.
- **C11** — `conf_get` semantics are **byte-identical** across `ask.sh`, `panel-models.sh`, and `doctor.sh` (regression-pinned).
- **C12** — A model id beginning with `-` (from env or config, bypassing `-m`'s `need_arg`) is refused with exit **2** — it must not be emitted as an opencode flag. A value-taking flag whose value is missing or starts with `-` is a usage error (exit 1).
- **C13** — Panel set resolution (`panel-models.sh`): explicit args > `$GUILD_MODELS` env > `modelguild.conf.local` `GUILD_MODELS`; comma- or space-separated; order preserved.
- **C14** — Panel de-duplicates (first-seen order kept, each dropped dup warned); warns on `<2` distinct models; warns if all models share one provider prefix ("diversity theater"); warns on a token that is not `provider/model`; exit **2** if no models at all. It does **not** consult the policy (that is per-call in `ask.sh`).

## C. Agent selection
*Oracle: `modelguild/ask.sh` (flag parsing, watch block, fallback blocks); `AGENTS.md` agent notes; `run-tests.sh` cases 1, 3, 3b–3h, 4, 14, 14b–14e.*

- **C15** (amended 2026-07-23, issue #36 — `--watch`/`guild-watch` retired at M12) — Default agent is `guild-read`. `--edit` → `guild-build`; `--research` → `guild-research`; `--watch` → `guild-watch` (**retired** with the witness at M12 — no watch agent ships; historical). `-a <agent>` overrides; an unrecognized agent runs as-is with a stderr note.
- **C16** (amended 2026-07-23, issue #34 — supersedes the bash-era fallback) — **A missing hardened def is a REFUSAL, never a fallback.** All four model-calling tools — `guild_consult`, `guild_panel`, `guild_research`, `guild_delegate` — refuse **unconditionally** when their hardened def (`guild-read` for consult/panel; `guild-research`; `guild-build`) is absent from **both** the project `.opencode/agent/` **and** the global `${XDG_CONFIG_HOME:-~/.config}/opencode/agent/` (`resolveAgentDefDirs` + `hardenedDefPresentIn` in `src/config.ts`, mirroring opencode's own `--agent` resolution order; fail-closed if absent in both). The refusal is a structured `agent-def-missing` result, **exit-analogue 5** (C57), **no model call, nothing logged** (gap parity). There is **no** silent downgrade to a weaker/unrestricted agent: the bash-era fallbacks (`guild-read`/`guild-research` → `plan`, `guild-build` → `build`, loud warning) are **removed** — a probe confirmed opencode also hard-errors on a message naming an absent agent, but the pre-flight refusal is the version-independent guarantee. The presence check governs **only** the tool's refusal decision, not opencode's own `--agent` resolution. `guild_panel` refuses the whole panel with one check (every member uses `guild-read`); `guild_consult` refuses even on a `sessionId` continuation (the def governs the agent regardless of session reuse). **This is STAGE ONE of two (issue #111, C73):** a filesystem presence check cannot observe whether opencode is APPLYING the file it found, and a def whose frontmatter opencode cannot parse passes this check while resolving with no default-deny floor at all. C73 adds the resolved-config stage behind it; this one is unchanged and stays in front.
- **C17** (amended 2026-07-23 — superseded by C16's unconditional refusal) — The bash-era `GUILD_REQUIRE_HARDENED=1` opt-in (which turned a fallback into a hard exit-5) **no longer exists** and is read by no code in `src/`: with refusal now unconditional there is nothing to opt into. Historical.
- **C18** — `--watch` has **NO fallback**: a missing `guild-watch.md` is exit **5** always (even without `GUILD_REQUIRE_HARDENED`), because any weaker agent could read the source and "audit" that.
- **C19** — `--watch` requires the watcher model be named explicitly; if unresolved (no `-m`, `$GUILD_WATCH_MODEL`, or `$GUILD_MODEL`) exit **8** — an empty id would let opencode pick its own default, possibly Claude, unchecked.
- **C20** — `--watch` refuses a Claude model (`anthropic/*`, `*claude*`, `*Claude*`) with exit **8** unless `GUILD_CONFIRMED=1` (then warns). Watcher model prefers `$GUILD_WATCH_MODEL` (env/config) unless `-m` was explicit.
- **C21** — `--watch` refuses to run when the effective `GUILD_LOG_DIR` resolves outside `<install>/logs/**` (exit 5) — the watch agent cannot read outside that scope, so an evidence-free audit is refused rather than produced.

### Read root, and the write root (issues #96/#107 — `src/worktree.ts`, `src/servepool.ts`, `test/worktree.test.ts`, `test/delegate.test.ts` section H)

- **C70** (added 2026-07-29, issue #96) — **A READ tool may be pointed at a git worktree of THIS repository, and at nothing else.** **The fence is `git worktree list`, enforced at ONE choke point** (`resolveWorktreeTarget`; C33a's discipline applied to a second caller-supplied path): the target is realpath-resolved and must be an exact member of the worktrees of the repository the server already resolved. **A target that does not validate is a REFUSAL that names the path** (`worktree-invalid`, exit-analogue **null** — there is no bash counterpart), never a silent fall back to the project root. It is refused **before any log write** (C24 gap parity) and routes no call anywhere. **The agent-def pre-check moves with the child** (C16's presence check, resolved against the serve root) — a worktree with no hardened def is `agent-def-missing` naming *that worktree's* dir, not a turn that dies on an unresolvable agent. **Scope, deliberate:** `guild_consult`, `guild_panel` (panel-WIDE — one root for every member, since members reading different trees would be incomparable while appearing to disagree) and `guild_research`. **`guild_delegate` did NOT take it, and now does — see C71** (issue #107). **Mechanism:** one supervised child per root (`ServePool`), never a restart of the shared one — a restart would kill a serve with other calls in flight — and the pool dies with the primary child through a single `OpencodeLifecycle.onShutdown` companion rather than a second copy of the stdin-EOF/transport-close wiring. **That companion runs on TEARDOWN reasons only, and the exemption is part of this clause:** the exempt set is exactly `idle` and `per-call`, with an **absent or unrecognized reason counting as teardown**, so a later reason can cost a respawn but never an orphan; each extra reclaims itself on its own idle timer. **A CONTINUATION'S ROOT IS THE SESSION'S, NOT THE CALL'S.** `GET /session/{id}`'s `directory` is the authority: the continuation is routed there, an explicit `worktree` that disagrees is an ERROR naming both, and a session whose directory is not a worktree of this repository is a refusal, never a guess. An **unfetchable** session refuses only where the answer could differ — this call named a root, or another root has already been routed in this server's life; with neither true the primary is the only child, the lookup decides nothing, and the call proceeds as before #96, which is what keeps the worktree-free continuation flows (`/guild:collaborate`, `/guild:workshop`) from depending on a new endpoint. Cost, stated: every continuation makes one short control-plane GET **before** the policy gate, so a continuation naming a denied model ensures a serve is up on the way to being refused (no model turn, nothing logged); a fresh call is unchanged. **THE READ ROOT IS IN THE RECEIPTS.** The `started` entry carries `read_root` when a non-default root was used. It follows C29's optional-field rule: written only when supplied, so an untargeted call's entry is byte-identical to one written before the field existed and no `verify()` branch changes. **Honest bound, part of the contract:** this is a WIDENING of what the read paths can read, and therefore of what can egress to a third-party model provider (C49/C50) — everything those clauses say about credentials and the web now applies to the targeted worktree too. It is enumerable, it belongs to the repository the user is already in, and it is opt-in per call (no target ⇒ behaviour byte-identical to before), but it is not a confidentiality boundary and is not claimed as one. A targeted worktree that already contains `.opencode/` also gets opencode's `node_modules`/`package.json` scaffolding written into it, while one with no `.opencode/` is untouched — **git-invisible only where opencode wrote the ignore file itself**, so a repo that COMMITS its own `.opencode/.gitignore` sees three untracked entries appear and a read-only review therefore visibly mutates the tree under review.
- **C71** (added 2026-07-29, issue #107) — **`guild_delegate` MAY BE POINTED AT A WORKTREE TOO, AND THE CAPTURE MOVES WITH THE CHILD.** The same `worktree` input, the same single choke point (`resolveWorktreeTarget` — no second validation path, no second refusal shape), the same `worktree-invalid` refusal with exit-analogue **null**, refused before any log write **and before any snapshot**. **THE WHOLE CLAUSE IS THE COUPLING.** The root is resolved **once**, and the ONE value is threaded to the serve child *and* to every capture consumer: the pre-turn snapshot, the throwaway-index baseline and after-tree, the ignored-file fingerprint, the submodule state, `scaffoldDigest`, the recorded patch and the recovery hint. `deps.repoDir` becomes an **input** to that resolution rather than a fallback beneath it, and `resolveRepoDir` is consumed inline so it is never bound to a local (issue #107). **That is a discipline, not a proof, and the contract says so:** `cwd` legitimately remains in scope — the evidence log takes it, since the log root is deliberately NOT re-rooted at the target — so nothing in the type system prevents a future edit handing it to a capture consumer. **THE RECOVERY HINT NAMES THE TREE.** A targeted call's hint is `git -C <worktree> checkout <tree> -- <path>`; the bare C39 form would restore into whatever tree the reader is standing in, since a worktree shares its main checkout's object database — silently wrong. An untargeted call's hint is unchanged. **THE WRITE ROOT IS IN THE RECEIPTS, IN ITS OWN FIELD.** The `started` entry carries `write_root`, NOT a reuse of #96's `read_root`: "this tree was mutated" and "the answer describes this tree" are different claims. Same C29 optional-field rule — written only when a target was resolved, so an untargeted delegation's entries are byte-identical to pre-#107 and no `verify()` branch changes; the `delegate-diff` is paired to it by `call_id`. **NO SESSION-AUTHORITY LOOKUP, deliberately**: `guild_delegate` has no continuation (no `sessionId` input, a fresh session per call, not kept), so the lookup would decide nothing. **The approval bridge parses the def IN FORCE IN THE TARGET TREE** — `approvalFor` receives the re-rooted `agentDefDirs`, so review finding H3's invariant (never gate a tool the agent's own def denies) holds along this new axis. **THE PRECONDITION IS RECORDED AT BASELINE, NEVER INFERRED**: `WorktreeSnapshot.opencodeDir` captures whether `.opencode/` existed *before* the turn, because afterwards it exists either way. **The `scaffoldChanged` FLAG never varies** — it always fires — and only the WARNING TEXT varies, across **three** cases: an existing plugin dir *modified* (review it); scaffolding *appearing* where `.opencode/` was already present (opencode's own first-run materialization is a **sufficient** explanation, explicitly **not** a claim that it is the whole of what appeared); and scaffolding *created* where `.opencode/` was **absent** (opencode does not scaffold such a tree, so this is an **unexplained** write into a directory `opencode serve` loads and executes — no benign reading is offered). Pre-warming the child before the baseline snapshot was considered and rejected (issue #107). **Cost, stated and not softened:** a delegated model can now edit files and run `bash` in a worktree the caller named, so C49/C50's accepted trusted-repo exposure — `guild-build` reads any repo file including credentials (#29), and `bash` reaches the network regardless of the tool-layer denies — extends to that tree. **TWO ACCEPTED RESIDUALS, named rather than left implicit.** (1) **`GUILD_AGENT_DIR` short-circuits the re-rooting**: `resolveAgentDefDir` returns that override before `projectDir` is consulted, so with it set both the def presence pre-check *and* `resolveAgentAllowSet` read the override while opencode itself still resolves from the serve cwd + global dir — meaning C66's H3 invariant is then checked against a def that is not the one in force. (2) **The `delegate-diff` entry carries no root**: `write_root` rides on `started` only — but the entry a reader consults when asking *what did this patch change?* does not itself name the tree, and the patch file lives under the **project's** logs regardless of which tree was edited. The pairing is by `call_id`. **The human diff review remains the boundary — of a diff that must be of the tree actually edited**, which is why the coupling above is the contract and not an implementation detail.

### The resolved-agent floor (issue #111 — `src/agentfloor.ts`, `test/agentfloor.test.ts`)

- **C73** (added 2026-07-29, issue #111; numbered as a suffix to the area) — **THE DEF CHECK IS TWO STAGES, AND THE SECOND ONE ASKS OPENCODE.** C16's presence check answers *does the def file exist?*; it cannot answer *is opencode applying it?*, and the gap between those is total. Frontmatter opencode cannot parse is applied in **NO part**: the permission map is absent entirely, the agent resolves on opencode's built-in `"*": allow` with no default-deny floor, and it is **silent** — no warning, exit 0, and the file on disk still reads as hardened. A control `guild-read` resolved to 19 rules ending `"*": deny` + its allow-set; the same def with one duplicate key (top level **or** nested inside the permission map) or one tab-indented line resolved to the 13 built-ins alone. Those two shapes are the instances currently known and are **explicitly not a closed list** — the condition is the parse. <!-- doc-size-exempt: #135 -->
  **THE CHECK IS OF THE RESOLVED CONFIG, NOT OF THE SOURCE** (maintainer decision, Ben, 2026-07-29). **AND IT IS AN EFFECTIVE ACTION, NEVER A PRESENCE TEST.** The action is computed **last match wins**, over the rules that can answer for an arbitrary invocation, for a probe tool no hardened def grants, and must be `deny`; that also catches a later `"*": allow` re-opening everything. `modelguild/tests/check-agent-permissions.sh`'s `effective()` is the reference for the semantics and the probe literal is deliberately the same one. Two refinements are part of the clause: the probe is a **sentinel name that is not a tool at all**, because a real denied tool (`task`) would falsely refuse a user who legitimately re-scoped their own def to allow it; and a `"*"` rule with a **narrow pattern** is not counted as a floor. **The sentinel has its own false-refusal class**: a def written as a **denylist** — every unwanted tool denied by name, no `"*"` rule at all — resolves nothing for the probe, so the effective action is *undefined* and the call is refused as "nothing matched" even though opencode applies that def perfectly well.
  **SCOPE AND PLACEMENT.** Every tool that refuses on a missing def carries it: `guild_consult`, `guild_panel` (**once up front for the whole panel**), `guild_research`, `guild_delegate`. **The C16 filesystem presence check stays in front, unchanged** — this is additional, not a replacement. It runs **after** the model-policy gate (so a denied model is still refused without contacting opencode), and **before** the approval pre-flight, before `log.newRun()`, and — on the write path — **before the GIT worktree snapshot**: C24 gap parity, a refusal routes nothing and writes no evidence run. **THE SCAFFOLD BASELINE IS HOISTED ABOVE THE GATE, AND THAT ORDERING IS PART OF THIS CLAUSE** (added 2026-07-30, maintainer decision, review A1). `snapshotScaffold` (the `scaffoldDigest` plus whether `.opencode/` existed) is captured **before** the gate, `snapshotWorktree` takes it as a **required** parameter so an omission is a type error, and the git half stays after the gate. Ordering it ahead of the approval pre-flight is load-bearing rather than tidy: C66's never-widen intersection is computed from the def **source**, so on a voided def the bridge would compute the narrow written allow-set while opencode allowed everything.
  **THREE OUTCOMES.** (1) opencode answers and the floor is in force ⇒ proceed, with the result **byte-identical** to a pre-#111 one (no field is added). (2) opencode answers and the floor is **not** in force — including an agent it does not list at all, which would answer HTTP 500 mid-turn — ⇒ **REFUSE**, kind `agent-unhardened`, exit-analogue **null** (deliberately **not** a reuse of C57's 5, which means specifically *the def is missing*), with a message naming the agent, the action actually resolved, the general catch-all rules in force, and the likely cause. (3) **opencode cannot be asked at all** — the control-plane call fails, or answers a shape the check cannot read ⇒ **PROCEED, AND SAY SO**, never silently: `agentUnverified` on the tool result (`structuredContent.agentUnverified`) **and** one stderr line stating the direction taken. **An `unverified` run with the APPROVAL BRIDGE ARMED loses more than that, so the note says so**: `agentUnverified` must state the gating may be **narrower than the set of tools opencode will actually run**. **The parse is strict in the same direction, everywhere:** one rule entry the check cannot read fails the **whole** array as unreadable rather than being dropped, because the entry dropped could be the floor — and a rule carrying **no `pattern`** is unreadable too, rather than being read as the universal one.
  **IT IS VERIFIED TWICE: ONCE BEFORE THE GATES, ONCE INSIDE THE TURN'S OWN SERVE LEASE** (added 2026-07-30, maintainer decision, review A3). `askViaAgent` re-verifies from inside the lease that will carry the session and the message (`PreTurnAgentCheck`), against the handle it is about to use, before the session is created. On the shared long-lived child that is a **cache hit and costs nothing**; under per-call mode it is a real check on the child that serves. Only an `unhardened` verdict stops the turn there — an `unverified` one must not — but it must still reach the caller: announcing is decided by the entry point against an `announced` set the CALL owns — deduped on the **child instance** within one call, not on the call — and the late verdict propagates into `structuredContent.agentUnverified`. **The late refusal also carries its own message unwrapped**, like the early shape, rather than the generic "the call failed" envelope. **THE CARDINALITY IS PART OF THE CLAUSE.** A late refusal lands after `log.expect()` and `log.started()`, and C24 requires exactly one `expected-call`, one `started` and one `completed` per `call_id`, checked in BOTH directions — so a refusal that merely returned would leave a run that FAILS `verify()`. It therefore throws (`AgentFloorNotInForceError`) and flows through the lifecycle's existing catch, which writes `completed` (exit 1, `capture_state: failed`) exactly as a model failure does: three entries, one `call_id`, and `verify()` returns the ORDINARY failed-capture verdict rather than a missing-entry one. On a panel it is a **per-member** kind, not a panel-wide refusal, because by then each member holds its own lease. The EARLY gate is retained precisely because it keeps the common refusal free of any evidence-log footprint at all.
  **WHAT IS CACHED IS `verified` AND NOTHING ELSE, KEYED ON THE CHILD INSTANCE.** A non-`verified` verdict is dropped and re-computed on the next call, and the warning **repeats per call** — that is the correct behaviour for "never silently", not a regression. The key is the child INSTANCE, not its URL: `ServeHandle.instanceId` is a per-process monotonic counter minted per spawn, so two handles carry it iff they are the same child, and a **base URL is a reusable loopback port, not an identity**. The URL remains a second key component, which can only make the key stricter (a miss, never a stale hit). **RETAINING `verified` PER CHILD IS CORRECT BY CONSTRUCTION:** the check and the enforcement read the SAME spawn-time config, and there is no state in which this reports `deny` while the child enforces `allow`. **The cost lands on RECOVERY instead, and it is real:** a user who does what the refusal says — fix the def, re-run `init` — **stays refused**, because the stale child is still serving, and `withServe` re-arms the idle timer on every entry, so retrying keeps that child alive past `GUILD_SERVE_IDLE_MS`. The refusal's remedy therefore **names getting a fresh child** and says why. Killing the child on an `unhardened` verdict was considered and deliberately **not** done: that is C70's finding-H1 shape (tearing down a child that may have calls in flight) and is a separate decision.
  **Honest bound:** the check is authoritative about what opencode **resolved** and says nothing about opencode's **enforcement** of it — `verify-guild-*.sh` remains the runtime proof — and C71's `GUILD_AGENT_DIR` residual is untouched, since this stage never reads a def file at all. Under `GUILD_SERVE_PER_CALL=1` the child that is CHECKED by the early gate is not the child that runs the turn; the verdict still transfers in practice, but nothing here may claim the checked child is the serving child.

## D. Evidence layer
*Oracle: `modelguild/log.sh`; `modelguild/ask.sh` (logging hooks); `run-tests.sh` log block (~L994–1620); `AGENTS.md`.*

- **C22** — Every model call writes **exactly three** lifecycle entries sharing one `call_id`: `expected-call` (before capture setup) → `started` (before the call) → `completed` (after). Three calls ⇒ nine entries.
- **C23** — Entries are paired by `call_id`, never by run_id+turn (retries and concurrent panel calls break turn-based pairing). `turn` is recorded for readability only.
- **C24** — `verify` requires, per `call_id`, **exactly one** of each of expected/started/completed — checked in **both directions** (a lone `completed` fails; duplicates fail; set-membership is insufficient).
- **C25** — `raw_response` is recorded **in full, always**, byte-exact via `jq --rawfile` (a `$(...)` capture that strips trailing newlines is a contract violation). `completed` carries `capture_state` ∈ {`complete`,`failed`}; a `complete` with a missing/absent response file downgrades to `failed`.
- **C26** — Prompt privacy `GUILD_LOG_PROMPTS` ∈ {`full` (default), `hash`, `off`}: `full` stores prompt text + digest; `hash` stores only a 64-hex digest; `off` stores neither. `verify` enforces each mode's shape.
- **C27** — Integrity is a hash chain (`prev_hash` = sha256 of prior line) **plus** a per-entry self-hash (`entry_hash` over the payload) covering the tail line the chain cannot. Hashes catch accidental corruption only — **not** adversarial rewriting.
- **C28** — `verify` also checks: valid JSONL, unique non-empty `expected-call` call_ids, capture completeness, prompt-mode/hash consistency, and referenced `delegate-diff` patch present + hash-matching. Integrity failure exits **7**.
- **C29** (amended 2026-07-28, issue #74 — the patch-less `delegate-diff`) — Entry types and claim flags: `claude-final` (the summary the developer read); `claude-disposition` **`claim:true`** (Adopt/Adapt/Reject/Defer, self-report to audit); `subagent-voice` **`claim:true, captured:false`** (a Claude subagent's turn, text in `claimed_response` not `raw_response`); `delegate-diff` **`claim:false`** (machine evidence, patch hash verified). Verdicts are validated to the four-value set. **A `delegate-diff` may carry NO patch artifact** (`EvidenceLog.diffUncaptured`): when the capture machinery itself throws there is nothing to hash, so the entry records `patch: null`, `patch_bytes: 0`, `files_changed: 0`, a **required** non-empty `incomplete_reason`, and **no `response_hash`**. That last field is what keeps verify's two branches apart: `capture_complete:false` fails the run on the **capture-completeness** check (the intended loud failure), while the referenced-artifact check — gated on a non-empty `response_hash` — never runs, so the entry is never reported as pointing at a MISSING patch it never claimed to have. Optional `incomplete_detail` (bounded crash text) and `scaffold_changed` are written only when supplied, so an entry without them stays shape-identical to one written before they existed.
- **C30** — A run of only well-formed `subagent-voice` entries verifies as non-empty (all-Anthropic exchange). Completeness bound: an unlogged subagent voice is undetectable (no durable pre-spawn marker), unlike a crashed opencode call which leaves its `expected-call`.
- **C31** (amended 2026-07-28, issue #74 — the "lost entry" guarantee is SCOPED) — Logging is best-effort and **must never fail the call it records**: every hook (including `mktemp`s) is guarded; the response `tee`'s status is read from `PIPESTATUS[0]`. A lost entry surfaces as a `verify` gap, never as a non-zero call exit or a silent success — **but that holds only for entries a cardinality rule requires.** C24 requires exactly one `expected-call`/`started`/`completed` per `call_id`, so losing any of those three is a gap `verify` reports. **Nothing requires a `delegate-diff`**, so a lost one is a *silent clean*: the run verifies, and the log cannot tell you an entry was ever owed. That was true before this amendment and simply unstated. The write path's compensation is `capture.recordFailed` on the tool result (C40) — not a `verify` gap, and deliberately not dressed up as one.
- **C32** (amended 2026-07-25, issue #23 — enforcement points, age rule, scope fences) — Retention: run dirs older than `GUILD_LOG_RETENTION_DAYS` (default 14; 0 disables) are pruned at **three** points, all resolving the window through one resolver so they cannot disagree: `new-run` (as before), **MCP server start** (added — a session that started the server and made no model call pruned nothing, so a project you stopped consulting kept its logs forever), and the **`modelguild logs clean`** CLI. Server start is **skipped** when `GUILD_LOG=off`: a user who turned logging off to freeze what is on disk keeps it. Prune only touches directories matching a minted run-id shape, only as **direct children** of the one resolved logs root (`GUILD_LOG_DIR` + `GUILD_LOG_PARTITION` applied — under partitioning only the current project's partition is in scope), and only where `lstat` says a real directory (a run-id-shaped **symlink** is never followed nor removed). A run's **age is the newest mtime found by a BOUNDED walk of its contents**, not the run dir's own mtime — a long-lived run whose `calls.jsonl` is still being appended is never pruned out from under itself. The walk's bounds are part of the contract, because they are what a maintenance path may not hang on: it descends at most **eight** levels below the run dir, `lstat`s throughout so a **directory symlink is counted but never descended** (it cannot leave the run dir or loop), and **skips an entry it cannot read**. Cost, stated honestly: a file that is newer than everything else in the run but sits deeper than that bound, or behind a symlinked directory, does not hold the run open — the age reads older than it is and the run can be pruned. The shipped layout is ONE level deep (`calls.jsonl`, `activity.jsonl`, `approvals.jsonl`, `meta.json`, `diff-*.patch`, and a `reports/` subdirectory), so the bound is a fence against a surprise tree, not a normal-case behaviour. A window that is **not a whole number** (a typo) resolves to *disabled*, not to the default: what cannot be read is never a licence to delete. Prune returns a result (removed run ids, ages, bytes, kept/skipped counts) and **never throws** — C31's posture extended to the maintenance path — and a `latest` symlink left dangling by a prune is dropped. **Layering (C9b) splits read from write here as it does everywhere:** the window is READ across every root layer (a global `GUILD_LOG_RETENTION_DAYS` binds in a project that never restates it), but only the **primary** root's `logs/` is pruned — that is the only root runs are ever written to, so the other layers hold no runs of ours and this project's prune has no business deleting from them.
- **C32a** (issue #23) — `modelguild logs clean [--days N] [--dry-run] [--dir D]`: with `--days` it uses that window; without it, the configured one. It **refuses** (exit 2, with the reason) when the configured window is `0`/disabled or unparseable, and when `--days 0` is passed explicitly — "no window" is never read as "delete everything". `--dry-run` reports what would be removed and deletes nothing. Exit 0 on success (including a logs dir that does not exist yet); 2 on a usage error or a refusal.
- **C33** — Partitioning: `GUILD_LOG_PARTITION=1` narrows the root to `<base>/<project-key>/<run>` (key = git top-level else CWD, base + short path-hash); stays under `modelguild/logs/`; disabled when `GUILD_LOG_DIR` is set explicitly. Default OFF ⇒ byte-identical to today.
- **C33a** (added 2026-07-28, issue #73 — run-id validation) — **A run id is a DIRECTORY NAME under the resolved logs root, so its shape is part of the contract.** C33 fences the root; this fences the child component. It is validated at **one choke point** (`#resolveRun` in `src/log.ts`) covering **both** supplied paths — the caller's `runId` argument and `$GUILD_RUN_ID`. The grammar is a single conservative path segment — an alphanumeric first character, then letters/digits/`.`/`_`/`-`, at most **128** characters, no `..` anywhere in it, and not a **reserved name** — `latest` (the symlink C34 maintains) or `watchers` (the approval bridge's presence dir, C67), compared **case-insensitively** — which excludes `/`, `\`, NUL and every other control character, a leading `.`, and whitespace. The minted shape (`<UTC stamp>-<hex>`) passes by construction. **Anything else is an ERROR, never a silent fresh-run fallback.** An EMPTY `runId` keeps its existing meaning of "absent, mint a fresh run". Four surfaces, each keeping the posture area D already holds elsewhere: an MCP tool's `runId` **input** is refused as a tool input error naming the tool, the field and the rule (`resolveRunIdArg`) **before** any work is done; the evidence layer's own refusal keeps **C31** (`ok:false` + a stderr warning naming the source — `runId` vs `GUILD_RUN_ID` — never an exception into the call) and writes **nothing at all**, not even a fallback run; `verify()` returns **code 7** rather than throwing (C31's audit-path posture, as in the IO case); and `modelguild watch --run` — the one place a human types a run id by hand — is a **usage error, exit 2**. **Bound, stated:** with `GUILD_LOG=off` nothing is written, so an invalid run id is simply never used; the tool-input refusal fires regardless of the logging state. `guild_delegate` applies the guard (`log.enabled() && runId.length > 0`) before touching the run dir, and reports the absent capture as `captureComplete:false` / `incompleteReason:"logging-off"` with the recovery hint — the model's work is never discarded by a logging-path failure (C31). **Same shape, two other components:** the `latest` symlink's target is read from disk and joined by `modelguild watch` without passing through `dir()`, so `latest()` returns a name only when it satisfies this grammar (an escaping target reads as *no latest run*); and `verify()` **basenames** a `delegate-diff` entry's `patch` field on READ as `diff()` already does on write, so a doctored entry cannot point the audit at a file outside the run dir on its way to failing the hash check. **Retention gap, stated:** C32's prune fence is a *different, narrower* predicate — the minted shape only — so a run id that satisfies this grammar without being minted (`my.audit.2026`) is **never pruned**, and its `calls.jsonl` can hold full prompts under `GUILD_LOG_PROMPTS=full`. The fence is not widened to this grammar (issue #73): sparing the user's own directories is why it exists.
- **C34** (amended 2026-07-28, issue #80 — multi-session on one root) — Concurrency: appends are serialized by a portable `mkdir` lock (stale-lock steal after ~1 min; drop-the-entry after ~10s rather than a torn unlocked append). That lock is **per run file**, which is precisely why it does not cover the multi-session case: two Claude Code sessions open on one project run two servers, and each writes its **own** run into **one** logs root — `calls.jsonl` is never contended between them, and the shared state is the root itself: the `latest` symlink and the retention scan. All three are part of the contract. (1) `latest` names the most recent run, and its refresh is **atomic** — a symlink at a temp name renamed over the old one — and **skipped when the link already names this run**. `ln -sfn`'s unlink-then-symlink pair leaves a window in which `latest` does not exist at all, and the refresh runs on **every** append, so a reader that re-resolves `latest` on every poll (`modelguild watch`, C63) genuinely lands in it — a hammering reader caught it absent repeatedly against racing sessions before this. A filesystem that cannot rename over a symlink falls back to the pair. **The atomicity is `rename(2)`'s and therefore a PLATFORM property**: POSIX specifies the replacement as atomic, and this repo exercises it on Linux only — the node suites do not run in the macOS CI job — so it is relied on, not proven here on both platforms. (2) **`latest()` answers only when the run directory is still there.** Prune deletes run dirs and only afterwards drops a dangling `latest`, and a second session may be pruning while this one reads — so the pointer names a deleted run for a real window, and answering with it would send a watcher to tail a file that is gone. A stale pointer therefore reads as *no latest run*, never as a run that vanished. The dangling drop re-reads the link immediately before unlinking, so it will not delete a pointer another session just repointed at a live run of its own: a **narrowing, not an elimination** — there is no unlink-if-target-matches syscall, which is why the existence check above is where the guarantee actually lives and the drop is **hygiene** (it keeps a human listing the root from finding a pointer to nothing). **There is no backstop for the remainder, and an earlier draft of this clause wrongly claimed one** ("the next append repoints the link anyway"): that is false exactly when the racing append was the run's LAST one — the `completed` of the final call, the ordinary way a run ends — after which `latest` stays absent until a later run starts and `modelguild watch` reports "no runs yet" for a run that finished fine. Sub-microsecond window, no evidence at risk, stated rather than papered over. (3) Retention passes racing each other and racing writers stay **data, never an exception** (C32's posture): a run being written is kept by the newest-content age rule, and a pass whose removal fails records the run as `skipped` rather than throwing. Two honest limits on the accounting, both observed rather than assumed: a run **can be counted removed by more than one pass** — `rmSync` with `force` swallows ENOENT, so two passes that both stat'd it before either deleted it both report it — so `removed` counts *removals attempted and not refused*, not distinct runs; and a concurrent removal (or a lock/run-dir `mkdir` landing inside the tree mid-walk) can surface ENOTEMPTY/EBUSY, which is why the removal **retries** and, if it still fails, leaves a partly-emptied dir that the **next** pass finishes — the run is still old and still in scope. Held by `test/log.test.ts` with real racing **processes** — synchronous fs calls inside one process can never interleave, so a same-process test would prove nothing here — with a reader hammering `latest` throughout.
- **C35** — Config knobs resolve **env override > `modelguild.conf.local` > default**, identically to `ask.sh`. Subcommands: `new-run`, `latest`, `dir`, `path`, `expect`, `started`, `completed`, `final`, `disposition`, `subagent-voice`, `diff`, `verify`, `prune` (usage error exits 2).

### The empty answer (issue #117 — `src/client.ts`, `src/consult.ts`)

- **C74** (added 2026-07-30, issue #117) — **A READ-PATH TURN THAT PRODUCES NO ANSWER IS A FAILURE, NOT AN EMPTY SUCCESS.** Both history extractors — the final text and the serving agent — stop at the last `user` message, so a continuation can never answer, or validate its agent, from an earlier turn. `guild_consult`/`guild_panel`/`guild_research` opt in (`requireAnswer`): an empty or whitespace-only final text is refused as `empty-answer`, exit-analogue null, quoting the turn's own `info.error` when opencode carried one. Such a panel member carries `error`, no `text`, no `sessionId`; a continued session is KEPT even under `keepSession:false`. `guild_delegate` does **not** opt in — an empty report beside a real patch is a successful delegation. `completed` keeps `capture_state:"complete"` and the byte-exact blank `raw_response` with `exit_code:1`, which `verify()` never reads, so the run verifies clean. **Bound: the unit is the TURN** — a preamble before a dead final message passes, returning the preamble.

### Live activity layer (issue #20 — `src/activity.ts`, `test/activity.test.ts`)

> **Adjacent to the evidence layer, deliberately NOT part of it.** The items above specify the
> *receipts* — the model's own words, byte-exact, captured for later audit. The items below
> specify *liveness* — a normalized trace of what the model is DOING, while it does it. Mixing
> the two would let a visibility feature weaken an audit guarantee; C59 is the fence.

- **C59** — Live activity is recorded to `<runDir>/activity.jsonl`, a **separate file**. No `calls.jsonl` entry shape changes, no entry references it, and `verify()` never reads it — so an activity file (present, absent, or corrupt) can neither pass nor fail an evidence run. Honest-guarantee statements are part of the contract here as they are in area G: these lines are **opencode's report of the model's ACTIONS at opencode's fidelity**, not receipts of its words (that is `raw_response`), and **not containment** — surfacing a `bash` call does not gate it, and the human diff review remains the write path's review point (C49, C52).
- **C60** — The normalizer's source is the **probed** event set (opencode 1.18.5, 2026-07-27), not the documented union: `message.part.updated` with `part.type === "tool"` is primary — its `state.status` walks `pending` → `running` → `completed`|`error`, carrying `tool`, `callID`, `input`, `output`, `metadata.exit` — plus `file.edited`, `permission.asked`/`.replied`, `session.idle`, `session.error`, and the delta stream. A tool invocation is **counted exactly once** — `toolCalls` and `byTool` increment on the first `tool-called` seen for a `callID` and never again, whatever the stream does afterwards — and the recorded LINES are deduped by **suppressing a repeat of the state already recorded** for that `callID`, which is what collapses opencode's repeated `message.part.updated` bursts into one `tool-called` plus one terminal line on every probed sequence. That is a suppression rule, **not a guarantee of one terminal line per invocation**: a stream that reported two *different* terminal states for one `callID` (`completed` then `error`), or that returned to `running` after a terminal state, would record each state change, because the recorder trusts opencode's state machine rather than second-guessing it. Where the dedupe key degrades it degrades toward under-counting, never inflation: with `callID` absent the key falls back to session+tool, so two concurrent invocations of the same tool in one session collapse into one. `pending` is **not** a `tool-called`: it carries `input: {}`, so treating it as one made the dedupe keep the inputless event and hid every shell command until after it ran — the trace is emitted on `running`, which carries the real input. **An event with no `sessionID` is broadcast to every subscriber of that serve child and flagged `unattributed`, never dropped**: `file.edited` carries only `{file}`, and routing it by session left `filesEdited` permanently empty against a real opencode. **Unknown event types are dropped silently** (an opencode bump must never break a call); a missing expected event degrades visibility only. Deltas are the stream's bulk and are recorded **only at `full` detail**.
- **C61** — **A stream failure is never a call failure** (C31's posture, extended). One `GET /event` subscription per serve child, refcounted and routed by `sessionID` — so a panel's concurrent members cost one stream, and an event that **carries** a session id reaches only that member. **The routing is not total, and C60 says why:** an event with no `sessionID` (`file.edited` is the probed case) is broadcast to every subscriber on that serve child, flagged `unattributed`, because routing it by session dropped all of them. So concurrent members on one serve child **do** see each other's session-less events, marked as unattributed — the ambiguity C63 reports rather than hides. Reconnecting with backoff, and closed when the serve child dies. If it cannot attach or drops mid-turn, the call proceeds and the result carries `activity.degraded` with a reason — **a quiet activity list must never be mistaken for a quiet model**.
- **C62** — Knobs resolve **env > `modelguild.conf.local` > default** (C35's order): `GUILD_ACTIVITY` default **on** (capability-neutral — it removes nothing and gates nothing; `off` opens no subscription, writes no file, attaches no summary; only the literal `off` disables, so a typo fails toward recording), `GUILD_ACTIVITY_DETAIL` default **`summary`** (tool name + truncated input) with `full` additionally recording raw event properties — which can carry tool OUTPUT, i.e. file contents the model read: **the same sensitivity class as `GUILD_LOG_PROMPTS=full` (C26), and the conf template must say so**. `GUILD_LOG=off` mints no run dir and therefore writes no activity file: turning the record off must not leave a different record on disk.
- **C63** — Two surfaces, both **conditional on the layer being on** (C62): with `GUILD_ACTIVITY=off` — or `GUILD_LOG=off`, which mints no run dir — no subscription is opened, no `activity.jsonl` is written, and no summary is attached, so there is nothing for either surface to carry. With the layer on (the default), neither surface has to be asked for. (1) Every model-calling tool result carries a **bounded** `structuredContent.activity`: counts by tool, every `file.edited` path, failed tools and session errors, the first N action lines with inputs truncated, plus `truncated`, `degraded`, and the file path (null until something is actually written, so a path always names a file that exists). **`filesEdited` carries a stated ambiguity, not a silent one:** because `file.edited` has no session id (C60), a path is exact for a single call and — where two write-capable calls share one serve child — attributable only to the child, not the member. A panel reports it **per member**, never merged — a merged blob would lose which model did what. (2) `modelguild watch [--run ID] [--dir D] [--no-follow] [--json]` tails the newest run's activity live, re-resolving `latest` so it can be started **before** the call exists. It is the primary channel precisely because it depends on nothing but a file and a terminal.
- **C64** — MCP `notifications/progress` are emitted **only** when the client sent a `progressToken` in the call's `_meta` (unsolicited progress is forbidden by the protocol), are throttled to at most one per second — an event arriving inside a window REPLACES the one being held and the held one is flushed when the window closes, so the developer always sees the most recent action rather than a stale one. **Intermediate events inside a window are not sent on this channel**; the complete record is `activity.jsonl`, and the progress stream is a sampled view of it, not a copy. They also heartbeat through a quiet stretch — which is what keeps a legitimately slow turn from tripping the client's MCP idle watchdog. The tool RESULT is byte-identical with or without them: this channel is strictly additive to the file and the summary, and it never carries an approval or a decision.

### Approval bridge (issue #20 slice 4 — `src/approve.ts`, `test/approve.test.ts`)

> **Opt-in, default OFF, and adjacent to the visibility layer rather than part of it.** C59–C64
> specify *seeing*; C65–C69 specify *answering*. The honest-guarantee discipline of area G
> applies here in full: this is attention and an interrupt, never containment.

- **C65** — **Default OFF.** `GUILD_APPROVE` ∈ {`off` (default), `write`, `all`} and `GUILD_APPROVE_EGRESS` ∈ {`off` (default), `ask`} resolve **env > `modelguild.conf.local` > default** (C35's order). `write` gates `edit`/`write`/`patch`; `all` additionally gates `bash`; `ask` on the egress knob gates `webfetch`/`websearch`. **An unrecognized value is an ERROR that refuses the call**, never a silent `off` — the opposite of `GUILD_ACTIVITY` (C62) and deliberately so: a typo failing quiet would leave the developer believing edits are gated when they are not. `GUILD_APPROVE_TIMEOUT_MS` (default 120000) is lenient by the same logic — an unusable value falls back, and the outcome is fail-closed either way.
- **C66** — **The bridge may only NARROW, twice over, and both are asserted mechanically at TWO points each.** (1) It emits **only `action: "ask"`** rules — never `allow`. (2) It gates **only tools the agent def in force already allows**, because `ask` on a *denied* tool converts it into an approvable one. Both are checked when the ruleset is built **and** again at the wire boundary in `createSession`, so no caller can route around the bridge. Both are load-bearing because a `POST /session` ruleset **merges** over the agent def's resolved array last-match-wins (probe P2): the single rule `[{bash,*,allow}]` demonstrably gave the read-only `guild-read` agent a **working shell**. **The allow-set is READ FROM THE DEF IN FORCE, never from a table** (amended 2026-07-28, review finding H3): the first implementation carried a hard-coded mirror of the three shipped defs and never compared it to the def actually resolved, so a user-hardened `guild-build.md` that denied `bash` still got `{bash,*,ask}` emitted — a user-denied tool turned approvable. A mirror cannot hold this invariant; only the def can. A def that cannot be found or **parsed** is a **refusal**, not a guess. Consequence, pinned: `GUILD_APPROVE` alone gates **nothing** on the read paths. The hardened agent defs are **unmodified** (C47/C48 unaffected).
- **C67** — **Armed with no channel that can answer ⇒ REFUSE up front**, before `log.expect()` and before the write path's worktree snapshot (C24 gap parity, C37 ordering): a refused call logs nothing and touches nothing. This is required, not defensive: under `opencode serve` an unanswered `ask` **hangs** the turn until `GUILD_MESSAGE_TIMEOUT_MS` — it does **not** auto-reject (probe P3 refutes the bash-era claim) — so arming blind deadlocks. A channel is either an MCP client advertising `elicitation`, or a live `modelguild watch --approve` (a heartbeat presence file under `<logDir>/watchers/`, fresh within 20s, `mode:"approve"`; a plain watcher does not count because it cannot prompt). `GUILD_LOG=off` removes the watch channel by construction — no run dir, nowhere to publish a request.
- **C68** — **Fail-closed, arbitrated by opencode, and counted from evidence.** An unanswered request is **rejected** after `GUILD_APPROVE_TIMEOUT_MS`; the reject carries a **message that reaches the model verbatim**, and the turn **continues** (a rejection is a denied tool call, not an abort). A bridge that loses the event stream while armed rejects everything still open and reports `approval.degraded` — so a quiet `requests: 0` under `degraded` means "we went blind", never "the model asked for nothing"; the turn is **not** killed. **The approval clock only ever starts on a request the bridge actually SAW** (issue #77). **On re-attach the bridge RE-LISTS opencode's open requests** (issue #91): `GET /permission`, filtered to the bridge's **own** session, ids it has already settled or already replied to are skipped, and the rest are routed as if their events had arrived, with the approval clock starting when they are *seen*. **The guarantee is "recovered on re-attach", never "never missed":** the endpoint is a snapshot of what is still OPEN, so a request raised *and* settled by another answerer during the window leaves nothing behind to recover. A failed or malformed `GET /permission` is a degradation, never a call failure — nothing in the re-list path may throw into a tool call, and it decides nothing, so both C66 invariants are untouched by it. **Two further bounds.** (1) A request this bridge already replied to whose reply did **not** take effect — opencode still lists it open — is **recorded and not retried**, keeps the bridge degraded, falls back to the turn's own backstop, and is counted under `unsettled`. (2) The re-list is the **approval** layer only, so **`activity.degraded` still latches for the whole call** (C63). Nothing runs ungated in any of these cases — opencode holds the gated call at its `ask` (C67's probe P3) — so the cost of the window is a **stall**, not an unprompted tool. **`approval.degraded` means "blind NOW", and it can CLEAR** — only on evidence: the bus re-attached, the list answered, everything it named for this session was routed, and nothing this bridge had already decided is still sitting open. What is latched instead is **`blindWindows`**, the honest caveat on every other counter: `degraded: false` with `blindWindows > 0` means the stream dropped and recovered, and that the counts for that window can under-report. `blindWindows` counts distinct periods of **unrecovered** blindness, **not** socket drops. `recovered` names how many requests came back through the re-list rather than the stream. Approvals use the session-scoped reply endpoint, rejections the message-carrying one; `always` is never sent by the bridge. **Arbitration:** both channels may answer and **first reply wins, with opencode as arbiter** (a reply to a settled id is a 404) — but elicitation must not *pre-empt* the other channel. A cancel therefore **abstains** while another live channel could still answer, and **rejects** when elicitation is the sole channel; an explicit *decline* always settles. **Counters report only what opencode accepted** — a reply opencode refused, or one that never left the process (`undelivered`), is not a decision, and `decidedBy` names the settler of each one. **A REFUSED REPLY IS CHECKED, not classified from its status code** (issue #97): **any non-2xx status opencode actually returns** is followed by one bounded `GET /permission` — the **same v1 snapshot the re-list reads, filtered to the bridge's own session**. **No status is excluded.** **Still open ⇒ the decision was not delivered**, counted under **`unsettled`** and carrying an **`unsettledReason`**. **Not open ⇒ the cause is named only where the status supports it:** a **404** is **`contested`**, and **any other status is `refused`**, which records what was observed and diagnoses nothing. **The check unable to answer — it failed, or the list carried an entry that could not be attributed and might be this one — ⇒ neither claim**: the request is still counted in whichever of those two the status selects, but recorded `still_open: null`. **`undelivered` is the transport arm alone** — nothing came back, no status to reason from — and the check is deliberately *not* run there. Every record carries the real `http_status` (`null` on the transport arm) and the bucket it was counted in. The check is **not restricted to the approve path**, it **decides and sends nothing**, and **it may never throw into a tool call**: every failure answers "could not tell". **Three properties of these counters.** (a) **`unsettled` is not refusal-only, and a reply still IN FLIGHT is not one.** It is fed by two observations of one condition, keyed by permission id: this re-check, and the re-list's own discovery that a request the bridge already answered is still open — which fires even after a **2xx** opencode accepted that did not take effect. The gate is "the attempt returned"; an in-flight request is recorded, counted nowhere, and does not keep the bridge degraded. (b) **The four buckets are DISJOINT and never sum past `requests`** — one classification per request id, a later observation superseding an earlier weaker one, `unsettled` being the only positively-confirmed one and therefore terminal. (c) **`unsettledReason` keeps the most informative reason, not the first** — an approve-path refusal outranks any other refusal, which outranks the re-list arm. So the C69a expiry condition is readable out of it **whenever an approve-path confirmation has happened at all**, and where none has, the field says what was seen rather than manufacturing a diagnosis; per-request detail is in `approvals.jsonl` either way. **What the check cannot see:** it reads the **v1** open-request list, so a request raised on a different permission surface is absent from it and reads `still_open: false` — true of that list, and not the same claim as "somebody else answered". **And it has a PANEL cost:** `unattributable` entries are deliberately not session-scoped, so on a panel sharing one serve child a **sibling member's** protocol-violating entry downgrades this check to unconfirmed for everybody. Accepted rather than fixed; the `still_open: null` record names the condition. **A refused reply deliberately does NOT feed `approval.degraded`.** The condition is surfaced by `unsettled`/`unsettledReason` and by the `not-delivered` record's `still_open` field instead, with **no threshold**. A confirmed-undelivered **approval** is also deliberately **not** retried as a *reject* down the endpoint that still works. This bridge fails closed on **silence**, never on a delivered decision. **The elicitation prompt is an EMPTY-FIELD form:** `requestedSchema` declares no properties, so the client's own **Accept/Decline** buttons are the decision in one keypress. All request context (command, model, tool, sanitized detail, the bash-approves-a-shell note, the edit-covers-write/patch note, the deadline) therefore lives in the **message**. **Only the literal action `"accept"` approves**; `"decline"` rejects, and *everything else* — `"cancel"`, an unknown action, a malformed result, a transport failure — is treated as a cancel and never as consent. **No tool input grants approval**, and the test asserts no tool's input schema carries such a field. Requests and decisions are recorded to `<runDir>/approvals.jsonl`, a **separate file** that `verify()` never reads (C59's fence, extended). <!-- doc-size-exempt: #135 -->
- **C69** — **A per-session ruleset is fixed at CREATION, and the session is CHECKED, not assumed.** opencode echoes the stored ruleset on session create and on `GET /session/{id}`; before the turn is sent, the bridge verifies that ruleset both **carries every required `ask` rule** and **carries nothing that widens the agent** (amended 2026-07-28, review finding M7: a subset check alone passed a continued session whose ruleset also held `{bash,*,allow}`, so the turn ran on a widened session while reporting itself armed). What that check does **not** claim: it inspects the session record, not opencode's resolved behaviour — proving the latter is `verify-guild-*.sh`'s job against a live serve. A build that ignored the field, a **continued** session created before the knob was armed, or a widened session all yield an `approval-not-applied` refusal with **no model turn**; running ungated while the caller believes the turn is gated is the one outcome this feature must never produce. A session created *with* the rules continues normally (the workshop round-1 → round-2 flow is unaffected). **Honest bound, part of the contract:** an approved `bash` is an approved **shell** — it can read credentials, reach the network, and spawn processes that raise no further requests. This is visibility and an interrupt; the human **diff review** remains the write path's boundary (C49, C52). One further honesty item, probed: opencode's `write` permission key is **inert** on 1.18.7 — `edit` gates the write/patch family — so `edit` must never be dropped from a tier, and the result reports the **effective** tool family alongside the literal keys.
- **C69a** (added 2026-07-29, issue #93 — numbered as a suffix so no existing C-number shifts) — **The bridge speaks opencode's v1 permission surface, and it is pinned there BY DECISION.** C66 governs what a ruleset may say and C69 governs proving it was stored; this clause fixes *which API expresses and evaluates it*, because on 1.18.7 those are not the same question. The pinned seam is the ruleset on `POST /session`, its echo on `GET /session/{id}`, the open-request snapshot `GET /permission`, and the two replies (`POST /session/{id}/permissions/{permId}` to approve, `POST /permission/{id}/reply` to reject) — the pair the server's bridge and the `modelguild watch --approve` terminal both answer, which is also what makes C68's first-reply-wins arbitration work. opencode 1.18.7 additionally exposes a **v2** surface (`POST`/`GET /api/session/{id}/permission`), and **the v2 evaluator does not consult the v1 ruleset stored on the session**. **Migrating onto it would therefore produce a turn that reports itself armed while the gated tool runs — precisely the outcome C69 forbids — and would fail SILENTLY** (the probe, the further findings and the correction history are recorded in the `V1 PIN` block in `src/client.ts`). One consequence belongs in *this* clause, because it bounds what C68's detection is evidence of: the list it consults is the **v1** one, so a **v2**-issued request id — which lives in the other store — reads as *absent* and lands in `contested`, not `unsettled`. **The half-migration described above is therefore still caught by C69's stored-ruleset check and by this pin, never by that counter.** **Revisiting has PRECONDITIONS, and reading this clause does not satisfy them:** a *fresh* probe on a *later* opencode showing that the v2 evaluator honours the stored ruleset, or the ruleset re-expressed in v2's own terms with C66's two invariants re-derived for that shape; **and** the `verify-guild-*.sh`-style live proof extended to cover it. **That first precondition is RUNNABLE, not prose:** `modelguild/verify-permission-surface.sh` — local-only, opencode-required, no model called — is **differential**: it evaluates the same action against a gated session and a control session on the same agent and judges whether the ruleset changed the answer. It covers **every tool family the bridge can arm** — bash/edit/patch on `guild-build`, webfetch/websearch on `guild-read` — and its PIN-HOLDS banner names the pairs it actually evaluated rather than claiming the surface at large. **It refuses to conclude** when the stored ruleset is not *structurally* intact (an exact `{permission, pattern:"*", action:"ask"}` entry), when a control shows the agent never allowed the tool, when both creates return the same session id, or when the rounds for **either** session disagree: an unstable sample is not a verdict in either direction. It reports the pin holding (exit 0), *ATTENTION — revisit #93* (exit 7), or INCONCLUSIVE (exit 6, distinct on purpose: "could not check" must never read as "pin holds"). **The pin also carries an EXPIRY CONDITION:** `POST /session/{sessionID}/permissions/{permissionID}` (`permission.respond`, the approve half) is marked **`deprecated: true`** in 1.18.7's `/doc` — the **only** deprecated operation in the whole document. That is not an argument for migrating (a deprecated endpoint that works beats a live one that gates nothing), but when it is removed, approvals will fail while rejections still land; C68's counters **detect** that rather than hiding it, and the response is to move the **approve reply** to whatever opencode offers then, re-verify with the probe script, and update this clause and the in-code record together — **not** to read that removal as licence to move the ruleset itself onto v2, which this clause answers on its own evidence. The mechanical half is `modelguild/tests/check-v1-permission-pin.sh` (CI): no **literal** v2 *permission* path (`/api/permission…`, `/api/session/…/permission`) may appear in a non-comment line of `src/`, and the in-code record must still be there. It is scoped to the permission surface on purpose; being a literal grep it does **not** catch the same prefix split or computed (`"/api" + "/permission"`, a `const V2 = "/api"` template, a `join("/")`, or `/api` folded into the base URL), nor a *new* permission surface under some other prefix. Those stay review judgment, against this clause.

### Installed-payload state (issues #22, #94 — `src/init.ts`, `src/notice.ts`, `test/init.test.ts`, `test/doctor.test.ts`)

- **C72** (added 2026-07-29, issue #94; renumbered from C71 on 2026-07-29, issue #113) — **THE SERVER UPDATES ITSELF; THE PAYLOAD IN THE USER'S REPO DOES NOT, AND THAT DIVERGENCE IS REPORTED.** **Every installed payload file is classified into exactly one of THREE states, from three hashes** — `recorded` (what init wrote), `current` (what is on disk), `shipped` (what the RUNNING package holds): **drift** (C-less, issue #22 — `recorded ≠ current` and `recorded ≠ shipped`: edited *and* the release moved on), **skew** (new here — `recorded === current ≠ shipped`: untouched and simply behind), and **unjudgeable** (no ownership record, so it stays unjudged; **explicitly not reclassified as skew**). A fourth combination is deliberately *nothing*: edited against the version the release still ships, where there is nothing to catch up to. **"Shipped" means the payload of the package the executing code was loaded from** — derived from `import.meta.url`, and cannot be redirected by a cwd or an env var. **Mode-correctness is INHERITED, not reimplemented:** each file is located project-then-global (`--global` ⇒ global only) and judged against the record of the location it was found in, both routed through `payloadDest`/`recordPathFor`, so a `--global` install is judged by the global record. **ONE detection, three surfaces** (`scanInstalledPayload`): `doctor`, the `guild_status` tool (`structuredContent.payload`, carrying the deciding installed-vs-shipped hashes), and the MCP server's start-up notice. **REPORT ONLY, and never a failure:** no file is touched, no `--force` is offered, and skew — like drift — **does not change `doctor`'s exit code**. `init` reports drift but **never skew**. **The start-up notice is the only UNSOLICITED surface, and it is bounded three ways.** (1) It writes to **stderr only** — stdout is the MCP transport — as a single block. (2) It is suppressed **per server version, not per session**. **The state is never written into the user's repository** — `$GUILD_ROOT` when one is pinned, otherwise `<home>/.claude/modelguild/.modelguild-notice.json` — and deliberately not in the ownership record. It is keyed on the **ownership record(s) the skewed files were judged against**, and a **global** payload shared by many projects is announced once rather than once per project. A version that cannot be read suppresses nothing, and the key is **the version string alone** — a republish under one version, a moving dist-tag, or development from a source checkout can move the payload while the notice stays silent; `doctor`/`guild_status` are the backstop. (3) `GUILD_PAYLOAD_NOTICE` ∈ {`on` (default), `off`} resolves **env > `modelguild.conf.local` > default** across the layered roots (C9/C35), leniently — only the literal `off` disables, so a typo fails toward telling the user — and governs **the notice alone**: `doctor` and `guild_status` report skew with it off. `GUILD_LOG=off` is deliberately **not** a second silencer (issue #94). **It may never break the server** (C31's posture, extended to start-up): the emitter cannot throw, and — because a `try/catch` cannot reach a *block* — the state read is gated on `lstat` saying a regular file, so a FIFO at that path cannot hang start-up before `connect`. The state write goes through a temp file and `rename`, which is both atomic and what stops it following a symlink out of the guild root; `safeJoin`'s refuse-any-symlinked-component rule is deliberately **not** applied, because a dotfiles-managed `~/.claude` is a symlink in a setup this repo documents. **A persistently unwritable state means the notice fires on EVERY start, not once** — bound (2) is the one that gives way. **DIRECTION IS NOT CLAIMED, and the wording says so.** Two hashes cannot carry it and the ownership record holds no version — correct in the normal case (the server moves, the payload does not) and wrong for a user who pinned an older server on purpose. Every surface reports the files as **out of sync with what this server ships**, states the usual cause, and names the exception, rather than asserting a direction it cannot see. **The remedy is VERSION-PINNED for exactly that reason:** `npx modelguild@<running version> init`, not plain `npx modelguild init`, which resolves the **latest** dist-tag and therefore does *not* converge in the pinned-older-server case. Where the version cannot be read the notice says so and names what the unpinned command would do instead.

- **C51** — **PARITY rule:** asymmetry is default-deny; do not restrict a non-Claude path more than the Claude path for the same task without a named harness difference. Vendor is not a threat model. `--auto` is a proven no-op for hardened agents and must not justify write-path friction.
- **C52** — External model output (including a delegate's report **and its diff**) is untrusted data for Claude to reason over or verify — never a command to execute.

- **C54** — `1` usage error (missing prompt, missing flag value).

each, that the ported behavior matched the bash oracle (test, live probe, or cross-verified log), with
